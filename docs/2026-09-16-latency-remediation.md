# 1440p60 전송 지연 수정과 실기 비교

## 결론

전송 예약 시각에 스케줄러의 늦은 기상 시간을 다시 더하던 오류를 재현하고 수정했다. 수정본을 Mac Host에 설치했으며, 실제 프레임별 전송 진단을 추가했다. **1440p60 전체 성능 기준은 아직 미달이다.** 빠른 UDP 설정은 Host 대기를 줄일 가능성이 확인됐지만, 비교 도중 다른 태블릿 테스트 앱이 전면으로 이동했으므로 정식 합격 또는 기본값 변경의 근거로 사용하지 않는다.

작업 근거: [선행 조사](2026-09-16-latency-improvement-research.md). 원본과 JSON 결과는 `artifacts/latency-remediation-2026-09-16/`에 있다. 이 문서는 이번 pacing 수정과 계측의 범위이며, 이전 입력·연결 변경의 전체 검증을 대신하지 않는다.

## 수정

### 전송 시각 누적 오류

기존 `paceUdpDatagram`은 예정 시각까지 기다린 뒤 실제 기상 시각부터 다음 간격을 더했다. 예를 들어 2ms 간격을 예약하고 0.5ms 늦게 깨어나면 다음 예약도 0.5ms 뒤로 밀렸다. 각 묶음에서 이런 일이 반복되면 실효 전송률이 떨어진다.

다음 예약을 **예정 시각 + 간격**으로 변경했다. 함수에 진입할 때 `max(현재 시각, 이전 예약)`으로 기준을 갱신하는 동작은 유지해, 긴 정지 후 무제한으로 몰아 보내는 동작을 막는다. 패킷 크기, 해상도, FEC 기본값, 자동 프로필은 변경하지 않았다.

생산 코드의 실제 시계·대기 함수를 사용하는 회귀 시험에서 구버전은 `wakeup lateness extended the next burst deadline by 512625 ns`로 실패했고 수정 후 통과했다. 오래된 예약이 무제한 전송 여유로 누적되지 않는 조건도 검사했다.

### 필요한 때만 켜는 프레임 진단

`LEFTCAR_FRAME_TRACE=1`인 Host에서 단일 스트림별 최대 36,000개 프레임의 JSON을 기록한다. 기본은 꺼짐이다.

- 프레임 식별: 스트림별 UUID, AU 번호, 캡처·인코더 출력 시각.
- Host 내부 단조 시계: 큐 대기, 패킷 준비, 예정/실제 pacing 대기, 늦은 기상 시간, 전송 호출 합계, 전체 처리 시간.
- 크기와 결과: 프레임 바이트, 실제/예상 datagram 수, 키프레임·복구 여부, 성공 여부.
- 화면 내용·키 입력·주소·인증 토큰은 기록하지 않는다.

`sendCallUs`는 재전송 기록과 암호화를 포함한 호출 시간이며 커널의 `sendto` 시간만을 뜻하지 않는다. 전체 처리 시간에는 마지막 JSON 기록 자체가 포함되지 않는다. 로깅 부하는 별도의 trace-off 비교가 필요하다.

## 검증 조건

- Lenovo TB710FU, Android 16, 동일한 설치 APK. 별도 성능 비교 앱을 설치하지 않았다.
- 2560×1440@60, HEVC RTVC, UDP, 동일한 Tailnet 주소 경로. 1080p로 내리지 않았다.
- 선택된 Android decoder: `c2.qti.hevc.decoder.low_latency`를 실행 로그에서 확인.
- Host encoder: `com.apple.videotoolbox.videoencoder.hevc.rtvc`. 하드웨어 속성 조회는 `unknown`이므로 조회 결과가 `true`였다고 주장하지 않는다.
- 실제 Chrome 전체화면의 고동작 texture/pan/rotation 장면을 Display 0에서 캡처. 원본 canvas 3840×2160, 전송 2560×1440. 시작/종료 태블릿 화면과 원본 cadence JSON으로 대응 확인.
- 화면 캡처는 설정 클릭과 장면 대응 확인에 사용했다. 측정 본문은 JSON/로그이며 주기적 미러링은 사용하지 않았다.
- 키 입력·물리적 표시 지연·외부 인터넷 경로·Parsec A/B는 이 영상 시험의 범위 밖이다.

A1과 B2는 시간대가 다르고 B2에서 프레임 진단을 켰다. 단 한 번씩의 결과로 개선율이나 회귀 여부를 확정하지 않는다. A1 로그 공백은 실제 정지인지 기록 누락인지 구별되지 않아 평균 출력률을 채우지 않았다. B1은 Chrome이 캡처 대상 화면에 실제 표시되지 않은 준비 오류로 중단하고 제외했다.

B2의 10,841개 전송 프레임에서 Host 큐 대기 p95는 **69.754ms**, 전체 전송 처리 p95는 **19.005ms**였다. 60fps 간격인 16.67ms보다 오래 걸리는 전송이 남아 있어, 시각 계산 수정만으로 대기를 없애지 못했다.

기존 기준을 유지했다: 출력 57fps 이상 표본 90% 이상, 캡처→Surface release 스냅샷 p95 50ms 이하, RTT p95 20ms 이하, 새 gap·복구·송신 실패·하한 압박 0. FPS 평균만으로 합격 처리하지 않았다.

### C1: 빠른 전송 비교는 중간에 무효화

설정은 custom UDP 16개 묶음, FEC 2, 자동 pacing 변경 꺼짐이다. 이 기존 프로필은 보통 delta frame 전송률도 2배로 높이므로 **묶음 수 하나만의 효과를 분리한 실험은 아니다.**

19:49:23 KST경 다른 테스트 앱이 태블릿 전면으로 이동했다. 따라서 181초 전체 기록과 전면 표시 검증은 실패했으며 정식 영상 비교에서 제외했다. Host 상태만 보는 gate는 PASS였지만 전면 앱 및 출력 기록 범위 검증이 이를 걸러냈다. 배경에서 계속되는 Host 전송을 실제 태블릿 출력으로 오인하면 안 된다.

전환 시점보다 4초 앞에서 자른 **106.17초 Host 진단 구간**은 다음과 같다:

| Host 프레임별 지표 | B2 자동, 전체 구간 | C1 빠른 전송, 전환 전 진단 구간 |
| --- | --- | --- |
| 표본 | 10,841 | 6,361 |
| 큐 대기 p95 | 69.754ms | 0.068ms |
| 전체 전송 처리 p95 | 19.005ms | 11.010ms |

이는 다음 재시험 후보를 고르는 근거다. 다른 조건의 시간 구간·비트레이트 적응이 포함되며, C1을 180초 영상 합격이나 장시간 안정성 근거로 승격하지 않는다. 원본 `c1-excluded.json`에 제외 시점·조건·진단 범위를 남겼다.

## 남은 작업과 현재 상태

다른 태블릿 측정과의 충돌을 확인한 후 고동작 부하와 이번 Host 스트림을 정지했다. 활성 스트림이 0개임을 확인한 뒤 Host를 일반 모드로 다시 시작해 프레임 진단도 껐다. 수정 앱은 설치된 상태이며 제어 서버 응답을 확인했다. 태블릿을 다시 차지하는 작업은 사용 가능 여부 답변을 기다린다.

1. 태블릿의 실험용 custom16 설정을 자동 설정으로 복원하거나, 전용 측정 시간을 확보한 뒤 자동/custom16을 번갈아 180초 이상 재측정한다. 현재 custom16은 임시 선택이며 기본값 채택이 아니다.
2. 기본 코덱 목록을 조회하는 읽기 전용 ADB 보조 프로그램을 준비했다. 실행·코덱 능력 확인은 아직 하지 않았다. 앱 설치 없이 실행하고 임시 파일을 지우는 방식이다.
3. 명시적 `rateControl` 요청은 현재 Host 코드에서 H.264 RTVC를 선택한다. 1440p Viewer UI는 해당 실험 선택을 숨긴다. 다음에는 기존 제어 API와 실제 decoder 변경 확인을 통해 H.264/HEVC를 비교할 수 있다. 동일 비트레이트 비교는 현재 자동 ABR 조건과 구별해 준비해야 한다.
4. 진단을 끈 상태의 재검증, 실제 한·영 키/트랙패드/가운데 클릭, 외부 인터넷과 장시간 발열은 미검증 상태를 유지한다.

성능 합격에 실패한 현재의 직접 근거는 Host 전송 대기, 지연·RTT 기준 초과, 자동 프로필의 복구 발생이다. 빠른 전송이 Host 대기를 줄인 뒤에도 남는 지연을 디코더 탓으로 단정할 자료는 아직 없다.
