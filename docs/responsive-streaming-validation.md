# 반응성 우선 스트리밍 검증

> 2026-09-07 작업 종료 시점의 전체 남은 작업과 재개 순서는 [마무리·인계 문서](2026-09-07-streaming-handoff.md)에 정리했다. 최신 Kotlin 전환 수정은 실제 Gradle 회귀 테스트 12개를 통과했지만 검토 지적이 남아 있으며, 아래 설치 APK에는 아직 포함되지 않았다.

## 적용 범위

2026-09-07 작업. 논리 데스크톱 크기와 전송 크기를 분리하고, 새 스트림의 반응성/선명도 우선 설정을 저장한다. 자동 선택의 최대 목표는 소스 비율과 픽셀 예산으로 정하며, 명시적인 기존 프로필은 사용자의 상한으로 유지한다.

| 소스 | 반응성 우선 시작 | 선명도 우선 시작 |
| --- | --- | --- |
| 3840×2160 | 2560×1440 | 3840×2160 |
| 2560×1440 | 2560×1440 | 2560×1440 |
| 5120×1440 (32:9) | 5120×1440 | 5120×1440 |
| 2160×3840 | 1440×2560 | 2160×3840 |

자동 전환은 시작 목표와 별도의 최대 목표를 보존한다. 반응성 우선으로 시작하더라도 상태가 안정되면 최대 목표로 올라갈 수 있다. 5120×1440은 7,372,800픽셀로 3840×2160의 8,294,400픽셀보다 적지만, 이 계산은 하드웨어 지원 증명이 아니다. 4K 듀얼 인코더는 기존의 정확한 3840×2160, 60fps, UDP 조건을 유지한다.

## 회귀 방지 및 통합 검증

- Android 복구 요청은 회차와 개별 요청 ID를 함께 추적한다. 이전 요청 결과가 최신 요청을 취소하거나 두 전송 경로를 동시에 여는 경쟁 조건을 막는다. 로컬 소켓 전송 성공을 수신 성공으로 해석하지 않는다.
- 일률적인 Host PLI 시간 제한 후보는 채택하지 않았다. 실제 새 손실 요청을 무시할 수 있기 때문이다. 전송 완료 뒤의 새 복구 요청과 아직 대기 중인 경계의 합류를 구분한다.
- Host가 수락한 인코더 모드와 Viewer 수신 준비 모드를 맞춘다. 구버전 요청에서 모드가 생략되어도 잘못된 4K 프레임 설정은 기존 스트림을 중단하기 전에 거절한다.
- 수신 FPS는 피드백의 나이가 확인될 때만 정책에 사용한다. Split의 실제 0fps와 지표 미제공을 구분한다. 캡처 대기시간 지표는 네이티브 JSON 파싱부터 상태 응답까지 전달하며, 구버전의 누락 값을 0으로 만들지 않는다.

현재 통과한 검증:

- Android/decoder 단위 테스트: 167+24개 통과, arm64 release 빌드 통과.
- Swift Split 테스트 실행 통과. 직전 복구 전송 시간을 실제로 설정해 시간 제한 회귀가 검출되는 조건을 유지했다.
- Host: 단위 테스트 141개 통과, 기존 2개 ignored. 통합 테스트 10개 통과.
- Control 계약: 15+19개 통과.
- React Doctor 100/100, 루트 및 Viewer 타입 검사 통과, Vitest 36파일 469개 통과.
- 실제 수신 준비가 부분 할당 후 실패하는 회귀를 먼저 재현했다. 정리 대상을 수락된 모드로 바꾸고 전체 검증을 다시 통과했다.

로그는 `/tmp/leftcar-responsive-validation/`의 `native-tests.log`, `android-release-build.log`, `split-test.log`, `host-tests.log`, `contract-tests.log`에 저장했다. 위 결과는 소스/빌드 검증이며 실기기 지연 개선 수치와 별개다.

## 실기기 판정 기준

녹화 입력 실험과 녹화 없는 애니메이션 재생을 분리하고, 실제 전송 크기 및 모드 변경 시각을 함께 기록한다. Android 명령 시작부터 녹화 화면 변화까지의 시간은 물리적 터치부터 광자까지의 지연이 아니다.

새 Host와 APK를 설치했다. APK SHA-256은 `1773be777ca0de13deacb1910f51bdda929ce5bac76a722cfced796b104c28a9`이다. 새 arm64 라이브러리와 Gradle 입력이 일치하고, APK 내부 라이브러리가 최종 strip 산출물과 일치함을 `apk-receipt.json`에 기록했다. 설치된 Host 카탈로그의 `reconfigureEncoderExperiment: true`도 확인했다.

1440p 자동 시작 관측에서는 100초 동안 2560×1440/단일 인코더를 유지했다. Host가 받은 수신 FPS 표본 중앙값은 54였다. 인코더 출력 FPS와 수신 FPS는 구분한다. 이 구간에는 측정 창과 Host UI 전환이 포함되어 있어 일정한 부하의 성능 벤치마크로 취급하지 않는다.

1440p 입력 녹화는 961개 프레임 중 960개에서 Host 프레임 ID를 읽었다. 시간표시 4개의 기준시각 편차는 0.467ms였으며, 원본 영상 PTS와 프레임 수가 일치하고 읽힌 ID가 역행하지 않는 것을 확인했다. 창이 좁아 프레임 ID 16비트만 사용했으며, 프레임 번호가 순환하지 않는 구간에서 Host의 프레임별 이벤트 기록과 연결했다.

| 입력 | 연결된 표본 | 명령 시작→녹화 화면 변화 중앙값 | 최대 |
| --- | --- | --- | --- |
| 탭 | 2 | 162.0ms | 209.5ms |
| 휠 명령 | 3 | 107.2ms | 232.9ms |
| 드래그 | 3 | 107.7ms | 118.2ms |

첫 탭 1회는 Host 입력 기록과 연결되지 않았다. 포커스가 원인인지 확정하지 않았으며 성공으로 세지 않는다. 작은 표본이므로 목표 지연 보장이나 기존 환경 대비 확정적인 개선율을 의미하지 않는다. 원본은 `responsive-input/analysis.json`, `injections.jsonl`, `host-events.jsonl`, `final.mp4`다.

4K의 녹화 없는 별도 측정에서는 같은 세션과 SplitVertical 모드로 약 180.38초를 관측했다.

마지막 행은 전체 프레임의 통합 P95가 아니다. 단기 재현 결과이며 변경 전과 네트워크 조건을 통제한 A/B가 아니므로 개선율이나 모든 정지 제거를 주장하지 않는다. 원본은 `clarity-no-record-android.log`, `clarity-no-record-host.jsonl`, `clarity-no-record-summary.json`이다.

첫 4K 입력 녹화 `clarity-input`은 **정량 판정에서 제외**했다. 측정 바코드가 좌우 인코더 경계를 가로질러 533번째 프레임 부근에서 섞인 ID와 음수 지연이 생겼다. 이런 값을 실제 반응 시간으로 보고하지 않는다.

4K 입력 재측정을 위한 원격 입력 활성화는 자동 승인 검토에서 접근 권한 변경으로 거절되었다. 해당 테스트 세션 동안의 허용을 별도로 요청했으며, 응답 전에는 입력을 다시 켜거나 다른 경로로 우회하지 않는다. 영상 재생 및 해상도 전환 검증은 이 입력 권한과 별도로 진행한다.

실기기 전환 검증에서는 추가 결함을 확인했다. 단일 인코더 1440p에서 같은 세션의 4K SplitVertical로 Host 전환이 수락되었으나, Android 기존 Surface 구성이 바뀌지 않아 새 renderer가 붙지 않고 6초 피드백 타임아웃으로 종료됐다. 원본 `live-roundtrip-android.log`와 `live-roundtrip-host.jsonl`; 이 경로는 추가 수정 및 재검증 대상이다. 창 표시 모드 변경 자체가 Surface를 중단시키는 실험도 별도로 있었고, 이를 해상도 전환 성공으로 세지 않았다.

기존 측정에는 약 2.895초의 복구 정지와, 녹화 없는 구간의 약 0.928초 복구 정지가 있었다. 평균 FPS가 높아도 긴 정지가 남으면 해결로 판정하지 않는다. 자세한 원본 조건은 `tablet-input-response-validation.md`에 있다.

현재 Host 카탈로그는 3840×2160 소스 한 개를 제공한다. 5K/32:9는 계산 및 계약 검증 범위이며 실재생 검증은 하지 않았다. 연결된 물리 마우스가 없어 물리 마우스 입력도 미검증이다.


## P0 마무리 실기 검증 (2026-09-07 저녁, Lenovo TB710FU)

P0-5·P0-7·P0-8을 마쳤다. 새 APK SHA-256은 `09b6ceacb9cbd5ef096b42c462f030e4a8bca56ed3eecbc96c17bed19c5c786e`이고, APK 내부 `libleftcar_viewer.so`가 release strip 산출물(`b853eb2e…`)과 일치함을 확인했다. Gradle 입력 라이브러리는 `54c3ae89…`로 빌드 산출물과 동일했다.

### P0-5 — TS mode-change 준비 연결 보존

`reconfigurePreparedStream`에서 Host가 split을 수락했는데 Viewer가 단일로 준비된 경우, 기존 코드는 Host 재구성 **이후**에 split 수신기를 재준비한 뒤 바로 열었다. 재구성은 이미 LCH1 챌린지를 발행했고 streaming replacement가 두 번째 챌린지를 보내지 않으므로, 새 split 프리플라이트는 빈 토큰을 받아 렌더러가 인증 실패한다(실기 session-3 피드백 타임아웃과 동일 계열). 수정 후에는 단일 준비를 취소하고 split을 재준비한 뒤 `encoderExperiment: "splitVertical"`로 재구성을 **다시 요청**해 새 챌린지를 받는다. 두 번째 요청이 split에 못 미치면 명시적 오류로 실패한다. 같은 모드 유지·강등은 기존 준비를 그대로 보존한다. `launch-stream.test.ts`에 reconfigure 경로 테스트 5개를 추가했다(총 27개 통과).

### P0-7 — Kotlin 전환 테스트 확충

`StreamSurfaceTransitionTest`에 3개 시나리오를 추가했다: 분할 화면 라이브 리사이즈(한쪽 destroy가 renderer 정지를 소유, 반대쪽은 무효), 디바운스 창 중 재구축(이전 계층 attach 영구 취소 + 늦은 create 무시), 1440p→4K→1440p→4K 4중 왕복. 실제 Gradle `:app:testReleaseUnitTest` 전체 41테스트 통과(전환 테스트 18개, 실패 0).

### P0-8 — 같은 연결 전환 매트릭스

절차: MainActivity와 StreamActivity를 모두 freeform으로 띄우고(스트림 시작 전), 하나의 뷰어 연결(instanceId `src-5001`, 재연결 없음)에서 크기 카드로 1440p→4K→1440p→4K를 구동했다. 측정은 신규 도구 `tools/stream-stats.py`가 제어 평면 `getStatus`를 1초 간격으로 폴링해 해상도·인코더 모드·renderedFps·프레임 갭을 기록했다.

| 전환 | 결과 | 전환 후 상태 |
| --- | --- | --- |
| 1440p(rateControl) → 4K(splitVertical) | 성공 | ~1초 내 rendered 56, 이후 59–61 유지 |
| 4K(splitVertical) → 1440p(rateControl) | 성공 | 60→58, 세션 유지 |
| 1440p → 4K(splitVertical) | 성공 | 42→59 상승, 5초 유지 후 적응형 정책 자동 1440p 하향(정책 동작) |
| 자동 하향 포함 재안착 | 성공 | 49–60 유지 |

Kotlin 로그에서 모든 전환이 pre-swap detach → retired holder destroy 무시 → 계층 재구축 → attach 반환 0(약 310–330ms) 순서로 진행됐다. 전환 매트릭스 세션(호스트 대체 세션 6·7)에서 오류·피드백 타임아웃은 0회였다. 기록된 유일한 `viewer connection lost (feedback timeout)`은 검증 절차상 freeform 재시작을 위해 `am force-stop`으로 종료한 첫 세션(5)에서 발생한 것으로, 전환 실패가 아니다.

한계: 세션은 reconfigure마다 호스트 대체 세션으로 교체되며(설계상 필수), 호스트 세션 번호 연속은 아니다. 물리 마우스·물리 터치→광자 지연은 여전히 미측정이다. 호스트 화면이 정적일 때 renderedFps가 1–25까지 떨어는 표본은 인코더/캡처가 정적 화면에서 프레임을 만들지 않는 정상 동작으로 판정했다(세션 상태 running, 갭 무증가).

원본: `/tmp/p0-verification/`의 `monitor.jsonl`(617표본), `logcat.log`.
