# Tailscale 뷰어 접속 실패 모드 진단

- 작성일: 2026-10-05
- 범위: `apps/viewer-expo/src/`의 뷰어 측 코드. 기존 조사: `docs/research/2026-10-05-tailscale-remote-access.md`
- 목적: tailnet 연결은 가능하지만 간헐적으로 실패하는 뷰어 측 코드 원인을 순위화한다. 호스트 및 실제 네트워크 상태는 이 범위 밖이다.

## 요약

확인한 실패 모드: **8개**. 상위 원인은 (1) 5초 TCP 연결 제한이 DNS 해석과 tailnet/DERP 경로 확보에 너무 짧을 수 있음, (2) 최근 호스트 후보의 순차 시도가 후보당 별도 제한 없이 누적되고 성공 기준이 TCP+암호 핸드셰이크까지만임, (3) 자동 재연결이 10초 간격의 단일 시도여서 일시적 tailnet 전환·복구를 놓칠 수 있음이다. 수정은 **뷰어 코드만으로 완화 가능한 항목과 정책·계측 변경이 있으나, 완전 해결은 불가능**하다. Tailscale 연결성, 기기 절전/네트워크 전환, DNS·DERP 상태는 외부 요인이므로 코드만으로 보장할 수 없다.

## 데이터 흐름 / 경계

최근 호스트 UI의 후보 생성은 `recent-hosts.ts`의 `resolveConnectCandidates`가 맡고, 같은 /24 → tailnet → 다른 사설망 → WAN 순으로 정렬한다. `RecentHostQuickConnect` 및 연결 경로가 `session.ts`의 `connectHostWithFallback`에 후보를 전달한다. 실제 소켓·secure-channel 핸드셰이크는 `control.ts`의 `connect`가 수행한다. 페어링 QR은 `connect-flow.ts`에서 대표 주소와 QR의 `ts` 주소를 순서대로 시도한다. 카탈로그가 광고한 추가 경로는 `mergeAdvertisedRoutes`가 최근 호스트에 병합한다. 계층상 적절한 수정 위치는 후보/재시도 정책은 `session.ts`·`recent-hosts.ts`, 소켓 단계별 타임아웃과 진단은 `control.ts`, 사용자 노출은 호출 UI다. Tailscale 상태 조회를 도메인 후보 정렬 코드에 직접 넣는 것은 경계 누수다.

## 실패 모드 (가능성 순)

| 순위 | 실패 모드와 코드 근거 | 영향 / 가능성 | 코드 대응 |
|---|---|---|---|
| 1 | **짧은 연결 제한 또는 DNS 지연.** `control.ts` `connect` 기본 제한은 5,000ms이며 그 안에 TCP 연결 및 secure hello 교환이 완료되어야 한다. 제한은 `setTimeout`으로 소켓을 파괴한다. MagicDNS 이름 해석 지연과 tailnet이 DERP 경로를 처음 협상하는 지연까지 별도 예산으로 구분하지 않는다. | 일시적으로 느린 경로를 실패로 판정. 다만 플랫폼 DNS/네이티브 소켓의 해석 동작도 영향. | 단계별 타이밍 계측 후 연결/핸드셰이크 제한 분리, 제한된 지수 백오프. 무작정 timeout 상향은 느린 실패를 키움. |
| 2 | **순차 후보의 총 대기시간과 잘못된 경로 우선.** `recent-hosts.ts`는 정렬만 하고 도달 가능성은 알 수 없다. `session.ts`는 후보를 하나씩 시도한다. 후보 수만큼 연결 제한이 소모될 수 있고, TCP가 성공해도 다음 후보는 시도하지 않는다. LAN 분류는 단순 /24 비교라 VPN·격리된 게스트 Wi-Fi에서 동일 대역 오판 가능. | 잘못된 LAN 주소가 먼저 선택되면 외부에서 접속 실패까지 지연. 성공 후보가 불안정한 주소여도 tailnet 대안을 즉시 탐색하지 않음. | 후보별 총 기한, 이전 실패 원인 기록. 병렬 경주 대안은 빠르지만 소켓 누수·세션 소유권 및 피어 식별 복잡성이 커서 기본 해법으로 권하지 않음. |
| 3 | **자동 재연결의 낮은 회복 탄력성.** `auto-reconnect.ts`는 최소 간격 10초를 두고 포커스 흐름에서 재시도 판단을 한다. 사용자 연결 해제 및 stale pairing이면 중단한다. 네트워크 복구 이벤트 기반 재시도나 짧은 백오프 연속 시도는 이 모듈에 없다. | 화면 포커스 타이밍과 일시적 네트워크 장애가 겹치면 사용자가 다시 시도해야 할 수 있음. | 연결 복구 이벤트/제한된 backoff를 추가하고, 사용자 중단·401 게이트 의미는 유지. |
| 4 | **TCP 연결 성공을 실제 연결 성공으로 오인.** `control.ts`는 secure handshake 완료 직후 `connect`를 resolve한다. QR 연결 흐름에서는 이후 저장·화면 전환이 가능하며, 첫 인증 명령이나 카탈로그 호출은 나중에야 호스트 응답성을 확인한다. | 중간 단계 실패가 연결 후 카탈로그 실패처럼 보이며 사용자에게 원인이 모호함. | 연결 직후 가벼운 인증 probe를 후보 성공 조건으로 삼는 방안. 비용은 왕복 지연 증가이며 연결 API 책임 변경 필요. |
| 5 | **QR 페어링에서 주소별 별도 시도와 제한 정보 부족.** `connect-flow.ts`는 `host`, 이어 `ts`를 fallback에 전달한다. 각 주소 시도가 개별 제한이며 오류는 마지막 오류만 던져 첫 실패 정보가 사라진다. QR의 `ts`가 없거나 오래된 주소면 tailnet 후보가 없다. | 주소 중 하나의 지연이 전체 페어링을 길게 하고, 오류가 원인·후보를 설명하지 못함. | 총 deadline 및 후보별 결과를 진단 로그에 보존. 호스트 광고/QR 생성 누락은 뷰어만 수정해 해결할 수 없음. |
| 6 | **호스트 주소 광고의 신선도·범위 제한.** `CatalogView.tailscaleHost`는 현재 광고된 주소만 `mergeAdvertisedRoutes`에서 별칭화한다. 오래된 recent-host 항목은 실패 전까지 다시 검증되지 않고, MagicDNS 이름 생성은 기존 조사에서 미구현으로 확인됐다. | IP 변경·광고 누락·오래된 별칭으로 후보가 불능일 수 있음. | 뷰어는 성공 주소를 우선 갱신하고 stale 주소를 관찰할 수 있지만, MagicDNS 광고는 계약/호스트 변경 필요. |
| 7 | **스트림 미디어 실패가 제어 연결 성공 뒤 별도로 발생.** `control.ts` 제어 TCP와 secure channel은 미디어 UDP 경로의 성공을 보증하지 않는다. `streaming-policy.ts`의 외부 경로 품질 캡은 초기 스트림 설정 정책일 뿐, tailnet direct/DERP 전환이나 UDP 도달성을 판정하지 않는다. | 페어링/카탈로그는 되지만 화면이 검게 멈추거나 미디어가 유실되는 증상을 제어 접속 실패로 오인할 수 있음. | 제어와 미디어 오류를 UI·텔레메트리에서 분리하고 수신 프레임/UDP 카운터와 RTT를 기록. 네트워크·호스트 측 점검 필요. |
| 8 | **제한시간 타이머 수명 관리.** `control.ts`의 connect-level `setTimeout`은 resolve 후에도 명시적으로 clear되지 않는다. settled 확인으로 성공 소켓을 뒤늦게 파괴하지는 않지만 타이머가 만료될 때까지 작업·클로저를 유지한다. 직접 실패 원인일 가능성은 낮으나 반복 연결 시 불필요한 타이머 누적이다. | 주로 자원/진단 노이즈이며 일반적인 간헐 실패의 주원인으로 볼 근거는 낮음. | 성공·실패·오류 경로 모두에서 timer를 clear하는 정리 함수로 수명 관리. |

## 수정 계획

1. **P0 계측:** `control.ts`에서 DNS/소켓 연결, secure handshake, 최초 probe를 분리 측정하고 후보 주소·단계·시간·오류 유형만 기록한다(토큰/비밀값 금지). 현상 분류 전에는 timeout을 크게 바꾸지 않는다.
2. **P1 deadline 및 정리:** connect 타이머를 정리 가능하게 만들고, 전체 사용자 동작 기한과 후보별 기한을 분리한다. 후보 시도 결과를 보존해 마지막 오류 하나로 원인을 덮지 않는다.
3. **P1 재연결:** 포커스 폴링에만 의존하지 않는 제한된 backoff/온라인 이벤트 재시도를 검토한다. 자동 재시도는 사용자 연결 해제와 pairing stale 게이트를 존중한다.
4. **P2 성공 판정:** TCP+핸드셰이크와 인증된 제어 probe를 구분한다. 후보 페일오버가 안전하도록 요청·세션 세대 소유권을 먼저 설계하고 테스트한다.
5. **P2 미디어 별도 진단:** 제어 연결 성공과 미디어 UDP 수신을 별도 상태로 사용자에게 표시하고, DERP 여부는 추측으로 단정하지 않는다. Tailscale 상태 API를 직접 쓸 수 없다면 사용자 기기 검사와 상관 분석만 제공한다.
6. **별도 호스트 작업:** MagicDNS 광고, `tailscaleHost` 신선도, 서버 리슨·UDP·DERP 성능은 호스트/계약 또는 실기기 검증 작업으로 넘긴다.

대안으로 모든 후보를 병렬 연결하면 대기시간은 줄지만 중복 secure handshake, 늦게 도착한 연결의 취소, 세션 교체 경합이 생긴다. 우선순위는 현재 순차 모델을 보존하면서 공통 deadline·단계별 관측을 추가하는 것이다. 이는 현재 뷰어 경계를 유지하고 복잡도를 제한한다.

## 기기 수동 검증 체크리스트

서로 다른 네트워크의 viewer/host 기기를 준비한다. 각 실행에서 시각, OS, 앱 버전, viewer 네트워크, host 네트워크, 호스트 후보 주소, 연결 단계별 지연, 성공/실패, 호스트 재시작 여부를 기록한다. 인증 정보는 기록하지 않는다.

- [ ] 같은 LAN에서 최근 호스트로 연결: 같은 /24 후보가 선택되고 카탈로그 및 스트림이 열린다.
- [ ] viewer를 외부 Wi-Fi/셀룰러로 옮겨 재개: LAN 후보 실패 후 tailnet 주소로 전환되고 연결된다.
- [ ] 앱을 백그라운드/포그라운드 전환하고 호스트를 재시작: 자동 재연결 및 수동 재시도 결과를 각각 기록한다.
- [ ] MagicDNS 이름과 100.x 주소를 각각 수동 입력/QR로 시도: DNS 지연, 인증 핸드셰이크, 최초 제어 요청을 구별한다.
- [ ] tailnet 비활성화 후 활성화, Wi-Fi↔셀룰러 전환: 반복 재시도 간격과 복구 여부를 기록한다.
- [ ] 연결은 되지만 UDP 차단/불안정 환경에서 스트림 실행: 제어 연결과 미디어 실패가 구분되는지 확인한다.
- [ ] pairing stale/401, 잘못된 host key, 호스트 전원 차단을 각각 시험: 네트워크 오류와 보안/인증 오류가 혼동되지 않는지 확인한다.
- [ ] 각 경우 5회 이상 반복하고 단계별 성공률·p50/p95 지연을 기록한다. 한 번의 성공만으로 신뢰성 개선을 판정하지 않는다.

## 미해결 사항

이 진단은 선언된 뷰어 코드와 기존 조사 문서에 한정되며 호스트 코드·Tailscale 클라이언트 구현·기기 로그를 확인하지 않았다. 특히 실제 실패가 제어 TCP인지 미디어 UDP인지, 이름 해석인지 DERP/절전인지 실측 근거가 없다. 따라서 순위는 코드상 취약 지점의 우선 조사 순서이지 현장 발생률을 증명한 통계가 아니다. 기기 검증 및 호스트 측 병행 진단 없이는 근본 원인을 확정할 수 없다.
