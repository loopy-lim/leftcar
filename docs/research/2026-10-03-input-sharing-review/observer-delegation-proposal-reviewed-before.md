# Proposed own-service observation delegation — approval required

Current evidence: [OEM report](oem-observer-readback-report.md) explains5fda0082 readback rejection through a protected original-caller gate. Shell already has ACCESSIBILITY_MOTION_EVENT_OBSERVING, app does not. Signature permission is not a normal user toggle. The approved helper currently builds input devices and input data; it does not apply the actual accessibility connection settings.

Proposed additional capability: only configure Leftcar's OWN already human-enabled accessibility connection through its existing authorized shell helper. No new global input monitor, UiAutomation, permission grant, OS hidden-policy settings, root, other app/service manipulation, touchscreen subscription, or network receiver in helper.

Concrete source scope if approved: native own-connection adapter, current AccessibilityService, authority and its local AIDL, fixed library dependency/keep rules, bounded capability errors/tests/setup documentation. No stream/Host/UI redesign change.

App adapter would invoke ONLY its own AccessibilityService.getConnectionId and AccessibilityInteractionClient.getConnection for that returned id, then obtain the returned IInterface Binder. Actual OEM getter is greylist-max-o and process-local: ordinary reflection cannot be assumed. Use exact pinned Maven Central org.lsposed.hiddenapibypass:hiddenapibypass:6.1 library targeted invoke/getInstanceFields APIs, with NO add/setHiddenApiExemptions calls. Read/write ONLY its own mMotionEventSources local dispatch field at native configuration boundaries; fail closed on unavailable API/layout. No per-input invocation. This is non-SDK access and a substantive architecture change, requiring approval before implementation/runtime.

New helper entry accepts connection Binder + existing fixed requested mask/mode only. Existing exact authorized app UID check remains. Validate exact service-connection interface and remotely obtained ServiceInfo's component class dev.leftcar.viewer.km.KmAccessibilityService and app UID/package against helper's trusted original app context before any mutation. Never accept caller-supplied arbitrary ServiceInfo, component/id, operation string, arbitrary source mask or app target. Build config from actual own service info; set mouse family or0 only, observed same/0 based on existing modes, toggle only existing key filter flag, preserve other fields. Invoke only that exact connection's setter and getter. Verify requested motion/observed values before success. No connection cache/retention beyond the call or new network capability.

Ordering: resolve/validate own connection and local dispatch field before helper settings write. Set the local dispatch field through a bounded own-instance adapter; helper applies directly as shell, without a preceding ordinary app setter that would create a consuming interval. Restore local field on failure; commit routing/owner only after verified system readback. Existing app public setter0 remains cleanup path (OEM permits observed0), returning local/system motion subscriptions and key-filter flag to0/OFF. Shizuku/connection death, stale preparation, unsupported member or cleanup failure must remain stopped/unconfirmed per existing lifecycle; no automatic rearming.

Acceptance: independent spec/security/source review; meaningful native tests for UID/target/source guards, failed/stale set/readback/rollback; exact Root normal Android build/signature/update-byte verification; human setup unchanged; actual edge/native hover-click-wheel-key roundtrip and recovery proof still required. No acceptance from reflection presence or getter equality alone. Preserve KeyBridge enabled and current own/external eligibility/lease gates.

Limits: this is a reviewable proposed route, not verified implementation or guaranteed device success. Maven Central metadata was read directly and release6.1 verified on2026-10-03; dependency digest and exact own-field/API behavior must still be verified before implementation; failure must stay explicit and closed. Direct shell application uses existing Shizuku permission but expands helper to a new private service-connection capability beyond its previously described device/input/release role.

Primary API references: https://github.com/RikkaApps/Shizuku-API (remote Binder vs UserService and non-SDK access); https://github.com/LSPosed/AndroidHiddenApiBypass (targeted invoke/field APIs; no global exemptions proposed). OEM exact methods/hashes in report provide device-specific gate evidence.
