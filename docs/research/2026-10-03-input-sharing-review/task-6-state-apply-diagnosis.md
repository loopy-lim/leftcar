## Exact State chain and silent-cancellation mechanism

Production receive → gate accept → `changeOwner` → queued-frame discard → `KmOwnerTransition.apply` → **releaseAll → releaseMouse → commitOwner → heartbeat acknowledgement** (`KmLifecycle.kt:16–26`, `KmRuntime.kt:84–87,320–334,364–401`). `commitOwner` checks authority/service and coexistence, configures OBSERVE for local/Mac owner or capture+CONSUME for Android owner, commits owner/status under the observation-session gate, then receive settles the exactly-once start completion under that same session gate. Initial placement is null, so the local-owner deferred-placement branch is not an ordinary first-State explanation.

`KmRuntime.stop()` **cancels the observation-session revision synchronously**, invalidates observation, then queues worker cleanup (`489–492`). Probe freshness is that admission revision. Later worker exception recording and `stopNow` terminal consequently suppress output (`startupFailure:118–119`, `KmHandshakeProbe.kt:20–30`). This is a concrete silent path after STATE_APPLY; logging does not bypass stale cancellation.

Masking race: if an external stop arrives while State is applying, service configure can fail its freshness/commit check and convert the cause to `KmObservationUnavailable` (`KmAccessibilityService.kt:46–76`). If cancellation arrives after configure but before Runtime's owner/status or start-completion commit, `check(commit(...))` instead throws an ordinary IllegalStateException. The current receive task's catch runs before the already queued external cleanup, calls `stopNow` and settles startup first with **unsupported** or the generic **startFailed/nativeHandshake** reason (`KmRuntime.kt:128–139,399–401,331–334,529`; `KmLifecycle.kt:73–80`). Later original cleanup cannot replace the exactly-once promise result. The panel also clears off-state reasons while no active peer exists (`use-km-model.ts:24–33`). Thus an original display/configuration-stop reason can disappear from startup presentation; generic failure does not exclude that trigger.

## Deadline, status and retry exclusions

- Native readiness deadline is 1000ms, posted on the same worker after Hello (`Runtime:281–287`); it cannot interrupt a blocking State task. If pending/current when it runs, it would emit STATE_WAIT FAILED plus STOPPED. A deadline alone does not explain this silent trace. App helper heartbeat runs every 100ms on that worker; the helper expiry timer is independent.
- JS has no independent native-handshake/readiness deadline. It awaits the native promise, checks abort/control identity, then requires armed/Mac-owner/Android-owner (`KmSession:83–90`). The control request timer belongs to the already completed startKm request, not native.start (`control.ts:453–469,476–490`).
- Low-rate native status events update panel status. Reconcile stops only **off with an active peer**; during pending startup active is null (`KmSession:127–138`). Status-driven rerenders alone do not cancel startup. The refresh/focus callbacks are stable; returning to AppState active refreshes, not cancels.
- None of these sources automatically retries prepare/start. A second admitted PREPARE implies a further call after native status became off; its trigger cannot be identified from the collector. It does not prove that the first failure was manually caused. No successful live input acceptance has been established.

Conclusion: the actual trace localizes this attempt beyond crypto/TCP to initial State application. **The strongest concrete lead is synchronous cancellation, with the unconditional configuration callback an especially plausible source-compatible trigger and a demonstrated reason-masking race.** The actual trigger is still unproved. Preserve the reviewed installed source; do not claim a fix or retry another APK on this evidence alone.
