## Supported feasibility, with limits

The OEM report establishes a relevant deployed-framework seam: a nonzero observed-source request is checked against the original Binder caller before identity is cleared. The ordinary app settings call loses the observed mask while shell has the relevant permission. Delegating the exact own connection would change that settings call's process, unlike merely constructing ServiceInfo in shell. This supports the proposed direction as a theoretical route; it does not prove that the private connection can be acquired or called successfully, or that the latest rejection had a separately recorded observed getter value.

The bounded own-instance resolver, mouse-only mask, preserved KeyBridge eligibility/lease gates, absence of a new monitor/network endpoint, targeted member access with no global exemption calls, no per-event reflection, and no automatic rearming are appropriate stated constraints. The interface should remain one closed configure operation, rather than exposing connection discovery, arbitrary Binder operations, or caller-supplied ServiceInfo.

## Important design gaps before privileged writes

1. **Complete transactional rollback and verification.** Proposal line 13 says restore the local field on failure and keep the existing public OFF setter. A setter can already have modified system subscriptions before a thrown readback, stale completion, failed local write, or rejected capture commit. Restoring only the local field can leave an active or consuming system subscription. Define rollback for each stage, including an uncertain setter result: release held synthetic input under existing cleanup rules, request OFF on the exact current own connection through the allowed cleanup path, restore the own local dispatch/routing state, and verify the postcondition. Never restore an active saved mask merely because it was the pre-call value after authority has failed. If system OFF cannot be established, remain cleanupFailed/unconfirmed with the existing explicit recovery path, not ordinary ready/off success. Current KmAccessibilityService.restoreLocal lines 53–63 checks only `serviceInfo?.motionEventSources == 0`; it does not establish observed-source zero or key-filter flag clearance. The new contract must state and check all required system/local OFF fields. The OEM public setter can swallow RemoteException, so a returned call is not success evidence.

2. **Exact own-target provenance and lifecycle.** Proposal line 11 requires the correct interface descriptor plus remotely returned component/package/UID. These constrain a truthful framework endpoint, but a descriptor and returned parcel are not independently authenticated proof of a caller-provided Binder's provenance. State whether the exact authorized UID is trusted to supply only a Binder obtained through the own-instance resolver; do not claim metadata alone enforces that stronger provenance invariant. If arbitrary caller-supplied endpoints are in scope for rejection, specify a feasible authenticity mechanism and counterfeit-endpoint tests. Resolve package, exact component, application UID including Android user, and enabled current own service against trusted app context rather than caller data. Bind the handle to the same own service instance/preparation generation before and after the call. Reject stale/reconnected/dead handles before commit and avoid cleaning a replacement using a stale transaction's saved field state. No cross-service connection enumeration is allowed.

3. **Finite modes and authority conditions.** The accepted `mask/mode` combinations and system/local postconditions are described informally in line 11. Write a closed table: OFF has ordinary/observed/local sources zero and key filter off; OBSERVE has mouse-only ordinary/observed/local sources; CONSUME has mouse-only ordinary/local sources and observed zero. Active key-filter state must match the existing native design. Reject all other combinations, touchscreen-family bits, unknown modes, and arbitrary source masks before mutation. Preserve the existing consent/current-authority/lease gates and transition eligibility: the new helper entry must not make CONSUME possible from a mere prepared/Armed observation state or a stale owner ticket. A bounded readback must verify mode-relevant flags as well as both source masks before success.

4. **Own-instance local bookkeeping and transition ordering.** The extracted OEM setter updates `mInfo`, calls `updateInputMethod`, writes `mMotionEventSources`, then sends settings; send clears `mInfo` and the connection's interaction cache. Bypassing that public path and changing only `mMotionEventSources` is not yet a demonstrated equivalent for the required local state. Document why omitted bookkeeping is irrelevant when other flags are preserved, or define the minimum exact own-instance handling allowed by approval. Also define the dispatch/routing mode while the local mask is staged before shell writes, including entry/exit of CONSUME. The correct ban on a preliminary ordinary app setter prevents the known denied-observed consuming interval, but does not itself prove every later partial-failure interval preserves local input. Prepare/transition serialization and generation checks belong in this operation's contract.

5. **Exact targeted access and supported fallback.** The pinned coordinate closes the version-selection gap. Artifact digest, required getter/connection/stub methods, field owner/name/type, and exact invocation route are still unverified. Review the pinned artifact's used path for global exemptions, initialization side effects, and Android/device compatibility; do not infer those from the targeted-method names. Specify an allowlist and fail-closed behavior for null/missing/wrong-type members, connection getter failure, field write/readback failure, and unsupported typed connection ABI. No broad field scan with arbitrary mutation, guessed Binder transaction codes, hidden-policy settings, global exemptions, or fallback monitor is permitted. Runtime feasibility checks that touch the private capability still require approval.

These are concrete contracts that an implementation must satisfy, not recommendations to broaden the capability or requirements to perform a device probe before the user chooses the direction.

## Approval-ready limits and required later proof

A user can approve the bounded new direction while acknowledging unsupported-device failure, with the above contracts made binding before settings mutation. The approval should not promise that private access or OEM shell invocation will work. If these gaps cannot be resolved within own-service/mouse-only scope, stop with an explicit unsupported capability rather than expanding targets, permissions, capture, or hidden-policy behavior.

After approval and contract completion: meaningful module-interface tests for UID/target/mode guards, stale/dead connection, uncertain writes, mismatched readback, field failures, rejected ownership commit, and rollback failure; independent source/security review; normal integrated internal Android build, exact signature/update-byte verification; then authorized user/device proof of non-consuming observation, real edge and hover/click/wheel/key roundtrip, and disconnect/authority-loss/cleanup recovery with KeyBridge enabled. Getter/reflection equality, library presence, compilation, and old artifacts remain separate evidence levels.
