# Lenovo 입력과 성능 후속 검증

2026-09-16 KST. Lenovo TB710FU, 일반 Leftcar 앱 `leftcar.ll3.kr`.
이 문서는 [1차 창 유지 검증](2026-09-16-input-window-validation.md) 이후 갱신한 Viewer와 Host의 결과다.

> 이후 실제 사용에서 두 손가락 스크롤·가운데 클릭·선명한 화면 실패가 추가로 보고됐다. 1080p 선택은 철회했고 최소 1440p를 따른다. 최신 수정과 아직 남은 실기 검증은 [포인터·선명한 화면 후속 검증](2026-09-16-pointer-clarity-validation.md)에 기록한다. 아래 수치는 이전 설치본의 측정 기록이다.

## 결론

- 연속 입력이 막히던 제어 응답 처리, 마우스 드래그, 키 누름 유지 문제를 수정했다.
- 실제 Lenovo에서 Android 입력 이벤트를 생성하고 Leftcar → 네트워크 → Mac → 검증 페이지까지 도착하는 경로를 확인했다. 기본 입력과 연속 입력 검증 모두 통과했다.
- 메인 창을 닫은 상태에서도 같은 영상 창에서 입력이 계속 전달됐다.
- 최종 1080p / 1440p 표본 모두 표시 FPS 기준을 통과했다. 다만 **전체 성능 기준은 아직 미통과**다. 1080p의 네트워크 RTT p95가 기준을 1ms 넘었고, 1440p에서는 프레임 공백과 복구가 발생했다.
- **물리 키보드·마우스 조작, 입력부터 패널 표시까지의 지연, Parsec와 동등한 성능은 미검증**이다. 자동 입력 성공으로 대신 판정하지 않는다.

## 합격 기준과 측정 범위

| 항목 | 이번 기준 | 측정 방법 |
| --- | --- | --- |
| 연속 표본 | 60초 이상, 수집 간격 최대 2.5초 | Host JSONL의 단조 시계 |
| 표시 FPS | 표본의 90% 이상에서 57FPS 이상 / 목표 60 | 수신기 FPS 상태 값 |
| 캡처 → Surface 출력 요청 | 표본 p95 ≤ 50ms | 수신기 `releaseCaptureAgeMs` |
| 네트워크 왕복 지연 | 상태 값 p95 ≤ 20ms | `receiverRttMs` |
| 프레임 공백·복구·송신 오류 | 구간 내 추가 0회 | 누적 카운터 차이 |
| 입력 정확성 | 누락·중복 0, 키 유지·드래그·수정키·스크롤 정상 | 검증 페이지 JSONL |
| 창 유지 | 메인 창 제거 후 같은 영상 Task 유지 | Android Task와 Host 세션 |
| 물리 입력 | 실제 연결된 키보드와 마우스 조작 통과 | 사용자 조작과 도착 로그 대조 |

이 값들은 이번 작업의 자체 기준이며 Parsec가 보장하는 수치가 아니다.
프레임 지연은 추정한 Host 시계 차이를 사용한 **Surface release 시점**이다. 디스플레이의 실제 발광 시점을 포함하지 않는다.
FPS·RTT 분위수는 상태 스냅샷들의 분위수이며, 모든 프레임 또는 모든 입력 이벤트의 분위수가 아니다.
누락 값은 0으로 바꾸지 않는다. 1080p의 release 표본 121개 중 유효 119개, 누락 2개를 별도 기록했다.

## 실제 수정

1. **암호화된 제어 응답 수신**: 전용 UDP 제어 소켓의 응답을 복호화하지 않은 채 평문 파서에 넘기고 있었다. 입력 ACK와 지연 응답을 복호화 후 처리한다. 잘못된 패킷·평문·재전송 공격 패킷은 처리하지 않는다. 실제 암호화한 ACK가 다음 대기 입력을 해제하는 회귀 테스트를 추가했다.
2. **디코더 출력 대기**: 다음 압축 프레임이 들어올 때만 준비된 출력을 꺼내던 경로를 수정했다. 수신 루프가 대기하는 동안에도 준비된 출력을 확인한다. 새 입력 없는 출력 확인이 캡처 메타데이터를 지우지 않도록 수정했다.
3. **드래그**: 마우스 DOWN/UP을 소비하지 않으면 Android ViewGroup이 Surface를 터치 대상에서 제외해 MOVE가 이어지지 않았다. DOWN/UP은 소비하고 실제 클릭 버튼 전송은 BUTTON_PRESS/RELEASE 경로에서 한 번만 수행한다.
4. **키 누름 유지**: 기본 키 라벨의 대문자와 입력 소문자 차이를 비영문 문자로 오판해 즉시 눌렀다 떼는 텍스트 입력으로 변환했다. ASCII 소문자의 비교를 정규화하여 실제 key-down/repeat/key-up을 유지한다. 비영문 문자 경로와 수정키 정책은 유지한다.
5. **60FPS 캡처 공급**: ScreenCaptureKit 설정에도 기존 CGDisplayStream 경로의 캡처 간격 여유를 적용했다. 생성 시와 커서 설정 갱신 시 모두 같은 정책을 쓴다. 실제 설정 팩토리의 회귀 테스트를 추가했다.

## 최종 성능 결과

동일한 로컬 전체 화면 페이지의 움직이는 막대를 사용했다. 각 구간에서 페이지가 표시되고 초점을 유지했으며, 브라우저 갱신 콜백은 약 59.97회/초였다. 이 콜백은 원본 화면 작업량 확인용이며 실제 패널 표시 증거가 아니다. 측정 중 빌드를 실행하지 않았다.

| 최종 프로필 | 유효 구간 | 표시 FPS p50 | 57FPS 이상 | 캡처 → 출력 p50 / p95 | RTT p95 | 공백 / 복구 | 판정 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 빠른 반응 1920×1080 | 61.46초 / 62개 | 60 | 60/62 (96.8%) | 22 / 28ms | 21ms | 0 / 0 | RTT 기준 실패 |
| 균형 2560×1440 | 61.53초 / 62개 | 60 | 57/62 (91.9%) | 30 / 47ms | 16ms | 1 / 2 | 공백·복구 기준 실패 |

1080p는 `stream-gate.py`가 검사하는 FPS·공백·복구·송신 기준을 모두 통과했다. 추가 지연 기준까지 합쳐 전체 합격으로 표시하지 않는다. 1440p의 한 번의 네트워크 손실 이후 수신기는 키프레임을 기다렸고, 일시적으로 상태 FPS가 33까지 내려갔다. 해당 표본을 제거하지 않았다.

이전 1440p 통제 표본에서는 캡처 공급량 약 57FPS, 표시 FPS 중앙값 54, 출력 지연 p95 48ms였다. 수신기 출력 처리를 수정한 다음 표시 FPS 중앙값 57, 지연 p95 36ms가 관측됐다. 최종 Host에서 캡처 공급량은 약 59.94FPS였다. 순차 진단 결과이며, 무작위 A/B나 변경 한 가지의 인과 효과를 증명하는 비교는 아니다. Host 갱신에는 작업 시작 전부터 존재하던 변경도 포함됐다.

이번 페이지는 가벼운 움직임이다. 게임·동영상·복잡한 스크롤·장시간 사용·XR 동시 실행을 포괄하는 합격 결과로 확대하지 않는다. 현재 프로필은 관측된 지연과 복구 기록을 바탕으로 **1080p60 빠른 반응**으로 두었다.

## 입력 검증

별도 Android 앱을 설치하지 않았다. 개발용 Java/Dex 도구가 Android 프레임워크에 정상 마우스 버튼 시퀀스와 키 이벤트를 전달하고, 일반 Leftcar 앱이 이를 처리하게 했다. 검증 완료 후 기기의 임시 Dex를 제거했다.

- 기본 검증: `a`, `Shift+A`, 왼쪽 방향키, `W` 누름 유지, 왼쪽/오른쪽 클릭, 스크롤, 드래그. 주입 수락 여부를 포함한 **9개 검사 통과**.
- 연속 검증: 키 down/up **50쌍**, 클릭과 드래그 버튼 down/up **51쌍**, 드래그 MOVE **120개**. 마지막 위치도 확인했다. 누락·중복 없음.
- 연속 검증 전후 메인 Task는 없었고, 영상 Task **497**이 유지됐다.
- 연속 입력 중 ACK 왕복 지연 평활값 29개: p50 **10ms**, p95 **11ms**, 최대 **12ms**. 이는 신뢰 입력의 전송 → 일치하는 ACK 구간이다. 입력 큐 대기·물리 장치 처리·호스트 UI 처리·패널 표시를 포함하지 않는다. 개별 입력 지연 분포로 표현하지 않는다.
- 최종 기기 목록에서 키보드팩은 존재하지만 비활성, 터치패드는 활성 상태였다. 물리 장치의 키 입력·버튼 변환·스크롤 방향·한글 IME·단축키·눌림 해제는 사용자 조작과 함께 확인해야 한다.

검증 페이지는 자기 페이지에 도착한 키 코드, 수정키, 버튼과 좌표, 시각만 기록한다. 입력한 문자 내용과 다른 앱의 입력은 수집하지 않는다. Host 페이지의 서버 도착 시각에서 ADB 시작 시각을 빼서 원격 입력 지연이라고 주장하지 않는다.

## 근거와 다음 확인

사용자의 후속 설명에 따라 클릭 위치와 조작 결과는 필요한 화면 캡처로 확인한다. 반복 측정은 코드·테스트·JSON 로그를 기본으로 한다. 세션 상태는 Host API, 창 유지 여부는 Android Task 텍스트, 입력은 도착 이벤트 JSON으로 확인한다. 물리 장치 조작은 사람이 수행하되 결과 판정은 같은 로그로 한다.

모든 원시 근거는 Git에서 제외된 `artifacts/input-performance-2026-09-16/`에 있다.

- `final-validation-receipt.json`: 최종 APK·Host·소스 해시와 검증 연결.
- `performance-summary.json`: 사전 기준, 이전 진단 구간, 최종 두 프로필, 실패 원인.
- `final-host-{responsive,balanced}.jsonl`, 대응 `*-native.log`, `*-metrics.json`, `*-gate.json`: 최종 성능 원시 로그와 판정.
- `final-host-input-main-closed.json`, `final-input-stress-main-closed.json`: 전체 입력 이벤트와 검사 결과.
- `final-runtime-state.json`, `final-input-device-inventory.txt`: 최종 세션과 장치 상태.

재측정은 일반 앱에서 원하는 프로필을 선택하고 같은 원본 화면·네트워크 조건을 고정한 뒤 수행한다.

```sh
python3 tools/stream-stats.py --device TB710FU --duration 62 --log /tmp/leftcar-run.jsonl
python3 tools/stream-gate.py --log /tmp/leftcar-run.jsonl --min-duration 60 --report /tmp/leftcar-run-summary.json
```

마지막 물리 입력 확인을 위해 Lenovo의 영상 창과 로컬 입력 확인 페이지를 열어 두었다. 키보드팩을 사용 가능한 상태로 펼친 뒤 `a`, `Shift+A`, 방향키, 키 누름 유지, 왼쪽/오른쪽 클릭, 드래그와 스크롤을 조작한다. 물리 조작 확인 전까지 이 항목은 `UNKNOWN`이다. 후속 성능 작업에서는 1440p 손실 후 복구 시간, 더 복잡한 화면과 장시간 구간을 확인하고 실제 Parsec 비교를 별도로 해야 한다.
