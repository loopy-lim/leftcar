# Wi-Fi Bidirectional Full KM Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. **Do not execute the privileged branch without explicit new approval.**

**Goal:** Direct-Wi-Fi Mac↔Android physical mouse (visible OS cursor, hover, buttons, wheel), keyboard and bidirectional edge crossing, with default OFF, directional consent and safe local recovery.

**Architecture:** Host owns one KM session state machine separate from streaming; existing authenticated peer control channel carries negotiation/state and direction-keyed reliable input transport carries transitions, with motion latest-wins. Native OS adapters consume authorized events only. Android accessibility observation is a capture seam, NOT an injection authority; the real Android cursor actuator remains blocked pending an explicit permission-route decision.

**Tech Stack:** Rust domain/control-contract/secure-channel, macOS Swift CGEventTap, Android Kotlin AccessibilityService/KeyBridge, Expo/React UI, USB ADB strictly for development diagnostics/install.

**Spec:** `docs/superpowers/specs/2026-09-25-wifi-bidirectional-km-design.md` with later transport decision `docs/superpowers/specs/2026-10-03-wifi-km-optional-usb-roadmap.json` taking precedence. Earlier TB710FU claims are not evidence for TB522FU.

## Global Constraints

- Product traffic: direct authenticated Wi-Fi app↔peer; wireless ADB is not a product dependency. USB is development install/diagnostics only; no USB product implementation in this plan.
- No root, lock bypass, auto-approval of OS permissions, or new privileged shell helper without explicit user approval. Preserve installed signature and app data; never uninstall or clear data.
- Full goal cannot be marked complete by gesture-only, text-only, keyboard-only, toggle-only, or a visible overlay impersonating an OS pointer.
- Both directions OFF until distinct peer consent and OS permission preflight; fail closed on disconnect, watchdog, lock, revoke, sleep, service death; release keys/buttons before returning local ownership. Never capture touchscreen. No automatic re-arm after reconnect.
- Any React/style/component changes require root `npx -y react-doctor@latest . --verbose` score 100 / 100, then typecheck and relevant tests.

## Device-specific evidence and decision

Read-only USB ADB on `HA2H8QSD` reports **Lenovo TB522FU**, Android **16 / API 36**, user/release build, installed `leftcar.ll3.kr` **0.1.10 versionCode 16 target 36**, APK signing digest abbreviated by dumpsys as `eea7996d` (not a full certificate fingerprint), app uid 10329. `dev.loopy.keybridge` 0.3.4 is separately signed (`49dcdc1d` abbreviated); enabled accessibility service is **KeyBridge only**. Leftcar manifest does not declare an accessibility service or privileged `INJECT_EVENTS`; `/dev/uhid` is `crw-rw---- uhid:uhid`, not accessible to the ordinary app. USB ADB shell uid=2000 has extra capabilities, **not transferable to app uid**. `settings get secure accessibility_enabled` = 1, with only `dev.loopy.keybridge/dev.loopy.keybridge.RemapService` enabled. These readings establish no app-level cursor injection grant. Mac TCC state was not reliably inspectable from read-only sqlite output; recheck manually in System Settings; do not infer permission from KeyBridge or screen streaming.

API 34 `AccessibilityService.onMotionEvent` and `AccessibilityServiceInfo.setMotionEventSources` (Android reference: https://developer.android.com/reference/android/accessibilityservice/AccessibilityService#onMotionEvent(android.view.MotionEvent), https://developer.android.com/reference/android/accessibilityservice/AccessibilityServiceInfo#setMotionEventSources(int)) permit service observation and consumption of selected mouse events; neither API injects a MotionEvent or registers a physical HID device. `dispatchGesture` injects touch strokes, not mouse hover/real OS pointer. `InputManager.injectInputEvent` / `android.permission.INJECT_EVENTS` are privileged, not a normal runtime permission (Android API reference: https://developer.android.com/reference/android/Manifest.permission#INJECT_EVENTS). UHID requires device node access unavailable to Leftcar uid. Therefore **no approved direct-Wi-Fi app-only full Android cursor actuator is established**. Full-goal implementation is blocked at this seam, not solved by completing the capture foundation.

**Decision alternatives (do not silently choose):** (A) Preferred product model: direct Wi-Fi app messages plus an independently approved platform/OEM-signed or managed system component with genuine Android input injection authority; requires concrete installability, API contract and user approval of elevated component/signing/device policy, then TB522FU cursor/hover test. (B) Explicitly approve a USB-started shell helper (or wireless-debugging-started helper separately), using shell-authorized `/dev/uhid`, with clear disclosure of debug dependence, lifetime/restart, scope and risks; product data may still traverse direct Wi-Fi, but startup depends on debugging and is NOT the previously approved pure Wi-Fi product contract. Need explicit approval for exact helper package, command, persistence policy and debugging mode before code/deployment; never launch via ADB as a diagnostic shortcut. (C) USB AOA HID: a separate future USB product extension, incompatible with Wi-Fi-primary-only mobility and unverified on TB522FU; require new scope/approval. If none accepted, record goal BLOCKED. Accessibility/IME gesture fallback is not an alternative meeting full goal.

**Attention to user:** Select A (provide system/OEM privilege route and authorize its deployment), B (explicitly authorize a USB-started privileged shell helper and its startup policy), or a new verified app-only real-pointer API with primary documentation and TB522FU proof. Otherwise work may advance on contract/capture/Mac components, but no full-KM success or unapproved helper implementation/install. OS permission prompts must be approved by the human in system UI, separately per direction.

## Boundary map and contracts

- `crates/domain/src/km.rs`: existing `KmStateMachine::new(KmCapabilities)`, `on(KmEvent)->Vec<KmEffect>`, `KmArrangement::try_enter/map_delta`; no sockets or platform handles inside domain. Add regression properties for any new trigger/authority transitions; effect order `ReleaseAllInjectedInput` before `RestoreLocalInput` and `BroadcastKmState`.
- `crates/control-contract/src/{common,host,viewer}.rs`: expose `km_share`, `KM_HELLO {session_id, epoch, capabilities, direction, peer_id}`, `KM_STATE {epoch, seq, owner, deadline_ms}`, `KM_INPUT {epoch, seq, origin, kind, payload}`, `KM_ACK {epoch, seq}`, `KM_RELEASE_ALL {epoch, origin}` as versioned schemas; use existing Rustra generator `crates/control-contract/src/bin/generate.rs`, reject unknown versions/kinds and bounds violations. Exact encoding should be locked by cross-language golden fixtures before consumers; session+epoch+origin avoids replay/feedback loops. Never piggyback stream input authorization onto KM.
- Existing secure-channel handshake/identity and direct Wi-Fi host↔viewer connection: authorize km_share independently per direction; derive direction-separated KM AEAD keys (HKDF `leftcar/km/v1` + session/epoch/direction); reliable ordered ACK/retransmit for key/button/wheel/text/release, latest-wins for relative motion; bounded queues and stale-epoch rejection. Verify socket/dispatcher entrypoints by `rg -n 'StartStream|InputOwnership|LCI1|LCS1|releaseInjectedInput' crates native apps` during execution rather than assuming generated names. Stream session remains independent.
- Mac shim `native/macos-capture-shim/Sources/Transport/CaptureSession+Input.swift`: existing `currentInputBounds()`, `injectPointerMove(_:)`, `injectPointerButton(_:)`, `injectScroll(_:)`, `injectKey(_:)`, `injectText(_:)`, `releaseInjectedInput()` are stream-coordinate receivers. Add a **separate KM native coordinator** and physical event-tap/secure-input preflight, mapped through domain geometry; use dedicated CGEventSource tagging to exclude synthesized events and an escape chord checked before suppression. Do not conflate stream-space and desktop-union coordinates.
- Android `km/{KmCaptureController,KmAccessibilityMotionAdapter,KmMotionSample,KmMotionSources}.kt`: already gated mouse-family capture, currently no registered Leftcar accessibility service; wire lifecycle only after separate user-enabled accessibility grant. `stream/KeyBridgeInputAdapter.kt` binds `IRemoteInputOwnership.acquire(): Boolean` / `release(): Unit` for stream; do not assume KeyBridge supplies mouse injection or silently modify separately signed KeyBridge. Define KM service ownership arbitration and explicit cross-process API or separate Leftcar service activation, with failure reducing capability to OFF. Android actuator is a separate `KmCursorInjector` boundary with `open(authority): Result`, `move(dx,dy)`, `button(code,down)`, `wheel(dx,dy)`, `key(code,down)`, `releaseAll()`, `close()`; **only implement against a user-approved verified OS authority**. Gesture or IME adapters cannot implement this full interface.
- UI/transport: peer-facing independent toggles/consent/revoke/status/error and explicit OS permission instructions; backend cannot arm without current authority acknowledgment and matching epoch. Render blocked capability as blocked, not partial success.

## Remaining risks

Existing foundation PASS is not device hardware proof. Installed Leftcar has no enabled accessibility authority; existing KeyBridge permission does not transfer to Leftcar. Mac TCC and TB522FU accessibility consumption behavior need physical validation. Above all, Android **injection**, not motion observation, is the unresolved architectural dependency requiring user attention. No product or device mutation was performed while authoring this plan.
