# Leftcar 지원 범위와 완료 기준

기준일: 2026-09-14. 공개 APK, 개발 소스, 로컬 패키지와 실기기 결과는 각각 다른 대상이다. 활성 PR #5 세션에서 사용자가 안정성 검사 시간을 60분에서 **30분**으로 줄인 결정을 반영한다. 이후 사용자는 화면 멈춤 때문에 새 디스플레이·가상 디스플레이 생성 실험을 제외하고 남은 작업과 30분 검사를 진행하도록 요청했다. 4K·XR·광학 지연의 다른 요구는 유지하며, 아래 조합이 통과됐다는 뜻은 아니다.

## 이번 마감선

첫 안정화 대상은 **macOS arm64 Host + Android arm64 Viewer + 같은 신뢰 LAN + 승인한 디스플레이 + H.264 단일 화면**이다. 1080p60에서 실제 영상 연결·정지·재연결을 세 번 확인한 다음 1440p·4K·다중 창과 장시간 조건으로 넓힌다. 이는 검증을 시작할 조합이며 현재 실기기 합격 선언이 아니다.

완료 단계는 다음과 같다.

| 단계 | 닫아야 할 조건 | 현재 증거 해석 |
| --- | --- | --- |
| 코드 통합 | 정확한 소스에서 회귀·타입·구조·React Doctor·플랫폼 CI 확인 | 후속 로컬 전체 검사·독립 검토 통과; 후속 원격 CI는 대기 |
| 내부 패키지 | 같은 source snapshot의 Host/APK, 내장 shim·JS·native·ABI·서명 검사 | 같은 소스의 내부 Host/APK 생성·직접 검사 완료. 설치·실제 성능은 별도 |
| 실사용 수용 | 그 패키지의 제어·미디어·입력·복구·장시간 시험 | 사용자가 추후 직접 검사하기로 한 범위 |
| 공개 릴리스 | 검증한 지원 조합, 배포용 서명·업데이트·복구·문서 | 내부 debug/ad-hoc 패키지와 구분 |

최종 로컬 산출물과 해시는 [후속 검증 기록](2026-09-13-completion-followup-validation.md)을 따른다.

실행 배경과 기준 소스는 [마무리 조사](research/2026-09-13-completion-readiness.md), 앞선 구현·실기기 시도의 상세는 [감사 개선 검증](2026-09-13-audit-remediation-validation.md)에 보관한다. 이전 패키지의 성공/실패를 새 소스에 소급하지 않는다.

## 사용자가 실행할 첫 검사

개인 화면이나 기존 프로필을 시험용 데이터로 바꾸지 않는다. 선택한 Host·Viewer 패키지와 **이미 존재하며 사용자가 캡처를 승인한 시험 디스플레이**를 명시하고 기존 장치·연결·설정은 보존한다.

현재 검사에서는 새 디스플레이를 만들거나 기존 디스플레이의 모드·배율·배치·활성 상태를 바꾸지 않는다. BetterDisplay·CGVirtualDisplay 등 외부 도구를 이용한 가상 화면 생성·크기 변경도 같은 제한을 따른다. 자동 복구나 정리 단계에서 해당 작업을 우회 실행하지 않는다. 필요한 해상도나 기존 source 수가 부족하면 그 조합은 미검증으로 남긴다. 재개에는 사용자의 새 명시적 승인이 필요하다. 스트림 인코딩 해상도와 Viewer 창 비율의 변경은 Host 디스플레이 자체의 변경과 구분한다. 소스 근거와 적용 범위는 [기존 디스플레이 검증 정책](2026-09-14-existing-display-validation.md)을 따른다.

1. Host와 APK의 build manifest를 `bun run release:manifest -- verify <manifest>`로 각각 확인한다. source snapshot, native ABI, 내장 JS, 서명 종류와 설치한 파일의 SHA-256을 기록한다.
2. Host를 실행하고 화면 기록 권한을 허용한다. Viewer를 페어링한 뒤 Host에서 **시험 디스플레이만** 해당 기기에 승인한다. 오디오·입력은 시험하기로 한 단계에서만 켠다.
3. 같은 LAN이라면 실제 Host LAN 주소와 제어 listener의 bind 주소·도달성을 먼저 확인한다. VPN·방화벽·OS 권한은 원인이 확인되기 전까지 가설로 둔다.
4. 제어가 연결된 뒤 Viewer의 실제 미디어 후보와 UDP 왕복 증명 성공, native decoder/render 카운터 증가를 확인한다. `127.0.0.1`의 제어 연결만으로 원격 Viewer의 UDP 도달성을 보장하지 않는다.
5. 변화하는 시험 화면으로 1080p60 시작→정지→재연결을 세 번 반복한다. 실제 출력이 없으면 그 실행은 미디어 실패로 남기고 장시간 검사로 넘어가지 않는다.
6. 10분, 30분을 순서대로 진행한다. 소스·패키지·네트워크·프로필이 바뀌면 별도 실행으로 기록한다.

현재 수집 명령은 `bun tools/perf-matrix/collect.mjs --help`로 확인한다. 입력 context에는 선택한 기기 serial·package·Host PID, 실제 workload, source/Host/Android manifest가 필요하다. 로그 버퍼 초기화나 자동 설정 변경을 검사 준비로 사용하지 않는다.

| 단계 | 수행 내용 | 완료 기준 / 기록 |
| --- | --- | --- |
| 기본 영상 | 단일 1080p60 세 번 | 실제 변화, decoder/render 증가, 종료 후 자원 반납 |
| 전환 | 같은 세션 1440p→4K split→1440p→4K 인코딩 해상도 전환, Viewer 창 비율, 반복 열기/닫기 | Host 디스플레이 모드는 유지. 잘못된 포트/Surface 재사용·timeout·누수 없음, 전송은 실제 지원 조합 |
| 제어·권한 | 입력 OFF, 허용 후 포인터/휠/드래그/수식키/한글 IME, 철회 | 승인 전 입력 없음, 종료·초점 이탈 후 눌린 입력 해제, 다른 화면 자동 대체 없음 |
| 복구 | 네트워크 단절, source 소실(디스플레이 제거 실험은 현재 제외), Host 종료, sleep/wake, background 30초 | 네트워크 회복 후 첫 표시 ≤1초, background 복구 ≤3초. 각 장애의 실제 복구 시점 기록 |
| 다중 창 | 1→2→4개 서로 다른 source, 비초점 갱신, Hub 종료, 한 창 오류 | 자원 초과는 시작 전 설명, 창별 격리·예약 반납, 실제 codec 인스턴스 기록 |
| K1 | 실제 3840×2160@60 입력 10분, 고변화 workload | 유효 encoder output·표시 평균 각각 ≥59fps. 평균 외 최장 정지·드롭 기록 |
| 30분 | 동일 조건 장시간 및 M4 다중 창 | 초기 대비 지연 p50 증가 ≤16ms, 메모리 지속 증가·반복 crash 없음, thermal severe 지속 여부 및 열·출력·복구 통계 보존 |
| 광학 | S1 glass-to-glass, 240fps 카메라 권장·200표본 이상 | p50≤50ms / p95≤80ms. 물리 입력 지연과 별도 분포 |

10분의 유효 수집은 30분 통과가 아니다. 과거 문서의 60분은 이전 목표이며 현재 마감 기준으로 요구하지 않는다. Surface release 시각은 물리 표시 시각이 아니며, collector의 stage 통계만으로 광학 지연이나 전체 4K 수용을 통과시키지 않는다. 충전 중 배터리 변화로 전력 개선을 주장하지 않는다. TB710FU 물리 패널 3200×2000과 3840×2160 인코딩 입력을 구분한다.

세부 절차: [성능 기준](06-benchmark-device-validation.md), [USB](usb-physical-validation.md), [Windows](windows-remote-host.md).

## 첫 사용·업데이트·프라이버시 확인

- 새 사용자가 개발자 shell 없이 설치→권한 안내→페어링→화면 승인→첫 영상을 진행하는지 관찰한다. 첫 영상 5분 이내는 권장 UX 실험 목표이며 측정 결과가 아니다.
- 잘못된 코드·카메라 영구 거부·오프라인 Host·승인 철회·저장 실패에서 다음 행동이 보이는지 확인한다. 한국어/영어·큰 글자·TalkBack·외부 키보드·종료 칩을 포함한다.
- 프로필/FPS/커서/오디오/클립보드를 저장하고 앱 재시작 뒤 확인한다. 백업 복원과 정상 앱 업데이트는 다른 시나리오다. 복원된 SecureStore 자격은 재페어링하며 기존 설정이 유지된다고 가정하지 않는다.
- 원격 화면 Activity의 recents·스크린샷 정책은 [플랫폼 권한 문서](platform-permissions-audit.md)를 따른다. FLAG_SECURE의 XR/Home Space 호환성은 실기기 게이트다.
- 새 설치·기존 공개 APK 업데이트·debug→배포 키 전환·Host 서명 변경을 각각 시험한다. 원본 데이터 삭제나 uninstall을 첫 복구 단계로 쓰지 않는다. 상세는 [버전·업데이트 안내](versioning.md).

## 공개 릴리스 중단 조건

아래가 열려 있으면 내부 후보와 공개 안정판을 구분한다.

- 배포할 조합에서 실제 영상, 권한 철회, 입력 정리 또는 요구한 장시간 조건 실패/미실행
- source·패키지·서명·ABI·내장 JS의 출처 불일치
- Android 배포 서명·기존 설치와의 업데이트 경로 미확정
- macOS Developer ID·hardened runtime·공증 또는 Windows 서명/설치 지원 정책 미확정
- 미해결 취약점·라이선스 검토 또는 사용자 정보가 포함된 진단 export 검토

불완전한 조합을 보장 목록에 넣지 않고 검증된 조합부터 공개한다. 릴리스 의존성 목록은 포함한 생태계와 미수집 범위를 표시하며, 목록 생성만으로 모든 라이선스/취약점 또는 공급망 attestation이 완료됐다고 하지 않는다.
