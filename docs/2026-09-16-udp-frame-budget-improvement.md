# 전송 시간 예산 수정: 기기 없이 진행한 개선과 Host 적용

## 결과

**Host에서 전송 대기가 누적되는 조건을 재현해 수정했고, 기존 Leftcar Host에 설치했다.** 태블릿을 점유하지 않는 실제 UDP 송신 시험에서 수정 전/후를 각각 3회 비교했다. 실기 영상 성능 합격은 아직 판정하지 않았다.

| 지표 | 수정 전 | 수정 후 |
| --- | --- | --- |
| 프레임 평균 전송 시간, 3회 중앙값 | 18.33ms | 15.40ms |
| 예정된 프레임 도착 대비 송신 시작 지연 p95, 각 실행 | 377.4 / 506.6 / 523.7ms | 9.6 / 14.9 / 8.8ms |
| 프레임 전송 시간 자체의 p95, 각 실행 | 25.3 / 27.1 / 25.5ms | 21.2 / 22.8 / 21.5ms |
| 매 실행 프레임 수 | 300 | 300 |
| 매 실행 송신 / 수신 패킷 수 | 18,387 / 18,387 | 18,387 / 18,387 |
| Host 로컬 전송 회귀 판정 | 3회 모두 실패 | 3회 모두 통과 |

60fps는 약 16.67ms마다 새 프레임이 도착한다. 전송 처리가 평균 18ms라면 약 1.3ms씩 밀려, 수 초 만에 수백 ms의 대기가 생길 수 있다. 수정은 이 평균 처리량 부족을 해소했다. **개별 느린 전송은 남아 있다.** 수정 후 전송 p95도 16.67ms를 넘으므로 모든 프레임이 한 프레임 간격 안에 처리된다는 뜻은 아니다.

## 재현 방법과 판정 범위

- 앞선 유효한 B2 실기 기록에서 연속된 일반 프레임 300개 중 총 크기가 가장 큰 구간을 선택했다. 원본 캡처 구간은 4.996초, 프레임 크기 32,367~110,227바이트다.
- 압축 영상 내용은 합성 바이트로 대체하고 크기만 재생했다. 비트레이트·묶음 수·FEC 강도는 인접한 1초 상태 표본에서 가져왔으며, 도착 간격은 정확히 60fps로 맞췄다.
- 실제 생산 코드의 패킷 생성, FEC, pacing, 재전송 기록, AEAD 암호화, UDP `sendto`를 사용했다.
- 목적지는 Mac 내부 IPv4 loopback이다. 패킷은 LAN 경로의 plaintext 1,400바이트 제한을 사용한다. 태블릿, Tailscale 터널, 실제 무선, 인코더·디코더·화면은 시험하지 않았다.
- 실행 순서는 수정 전1 → 수정 후1 → 수정 전2 → 수정 후2 → 수정 전3 → 수정 후3이다. 실행 중 이 작업의 빌드나 UI 조작을 병행하지 않았다.
- 로컬 회귀 기준: 송신 성공과 송수신 패킷 수 일치, 평균 송신 시간 <16.67ms, 누적 시작 대기 p95 ≤33.334ms. 이 기준은 Host 송신부 재현용이며 기존 180초 영상 성능 기준을 대체하지 않는다.
- 각 실행 약 5초인 짧은 진단이다. 장시간 안정성·무선 혼잡·기기 발열의 근거로 사용하지 않는다.

별도 성능 측정 APK는 설치하지 않았다. 재현 도구는 저장소의 명령행 프로그램이다.

```sh
tools/build-macos-capture-shim.zsh udp-send-probe /tmp/leftcar-udp-send-probe
/tmp/leftcar-udp-send-probe artifacts/latency-frame-budget-2026-09-16/high-motion-fixture.json
```

## 원인과 수정

기존 계산은 압축 AU 크기에 FEC 비율을 곱해 전송률을 정했다. 실제 datagram의 헤더, FEC 마지막 그룹의 패딩, singleton tail 중복 전송, 암호화 및 IPv4/UDP 헤더는 그 비율과 정확히 일치하지 않는다. 고동작 프레임의 pacing 예산도 거의 한 프레임 간격 전체를 사용해 패킷 준비와 스케줄링 지연을 흡수할 여유가 작았다.

새 `UdpFramePacingBudget`은 준비된 datagram들의 실제 바이트 합계에 암호화 24바이트와 IPv4/UDP 28바이트를 패킷마다 더한다. 전송률과 묶음당 비용을 같은 바이트 기준으로 계산하고, 프레임 간격의 80% 안에 pacing을 예약해 나머지 20%를 준비·스케줄링에 남긴다.

- 단일 UDP 스트림의 일반 프레임에 적용한다.
- 묶음 크기, 패킷 내용, MTU, FEC 강도와 압축 프레임의 참조 순서는 유지한다.
- 키프레임 복구 경로, TCP와 split 전송은 기존 경로를 유지한다.
- 추가 시간 예산 가속은 기존 high-motion 기준인 120Mbps로 제한한다. 이미 설정된 전송률이나 기존 custom16 배수까지 새롭게 전역 제한하는 변경은 아니다.
- 압축된 프레임을 건너뛰거나 해상도를 1080p로 내리는 방법을 사용하지 않았다.

헤더 누락과 준비 시간 여유를 함께 고친 변경이다. 이번 비교만으로 두 항목의 독립적인 기여율을 나누지 않는다. 20% 여유는 로컬 재현에서 유효했던 후보 값이며 모든 네트워크의 최적값으로 확정하지 않았다.

## 검증

- 수정 전 실제 송신 재현: 평균 17,890µs, 대기 p95 377,409µs로 실패.
- 수정 후 같은 재현: 반복 3회 모두 로컬 회귀 기준 통과.
- `UdpFramePacingBudgetTests`: 72개 패킷 생성/예산 조합 통과. LAN/Tailscale 크기, FEC 2/3/4, 묶음 2/4/8, singleton tail과 부분 그룹을 포함한다. 추가 가속 상한과 키프레임 격리도 확인했다.
- 기존 `policy-test`: 통과.
- 최적화된 shim 및 재현 도구 빌드: 통과.
- 이번 변경은 Swift와 명령행 도구·문서에 한정된다. React/React Native 소스 변경은 없다.

## 남은 검증

태블릿을 독립적으로 사용할 수 있을 때 자동 전송 설정으로 복원한 뒤, 같은 고동작 1440p60 장면으로 180초 이상 비교한다. 전송이 빨라진 대신 무선 손실·RTT·복구가 늘어나는지 함께 판단해야 한다. 결과에 따라 20% 여유를 조정하거나 되돌린다.

기존 영상 기준(출력 안정성, capture→Surface release p95 50ms 이하, RTT p95 20ms 이하, 새 gap·복구·송신 실패 0), 실제 키보드·IME·마우스, WAN·장시간 검증과 Parsec 비교는 미검증으로 남긴다. Host 송신 병목을 줄인 결과만으로 이 항목들을 합격 처리하지 않는다.
