# 태블릿 입력과 화면 반응 후속 검증

2026-09-07 11:32–11:52 KST. TB710FU / 기존 4K SplitVertical 세션 5.
결론: 일반 구간의 반응은 개선됐지만, 영상 손실 후 복구 정지가 남아 있어 안정성 완료가 아니다.

## 방법과 경계

- Loop/Z.AI `glm-5.3-flash` worker `01a079b6-f54f-7542-970e-b23b6d2f2429`가 입력 경로를 읽기 전용으로 검토했다. 실기 조작은 루트에서 직렬 실행했다.
- Host의 시스템 입력 권한은 이미 승인되어 있었으나 해당 세션 입력은 꺼져 있었다. 검증 중에만 세션 입력을 켰고 종료 후 꺼짐으로 복원했다.
- 임시 Mac 테스트 화면이 프레임 번호와 입력 상태를 흑백 코드로 표시하고, 클릭·드래그·휠 도착 시각을 기록했다. 제품 코드는 이 후속 검증에서 변경하지 않았다.
- Android 기본 `input` 명령으로 터치·드래그·휠 이벤트를 전달하고, 1280×800 screenrecord의 시간 오버레이와 프레임별 상태를 대조했다. 물리 터치 센서나 패널 광자 시점은 측정하지 않았다.
- Android 명령 실행 직전 장치 시각부터 녹화 화면 반응까지의 값이다. 명령 시작 비용과 화면 녹화 경로를 포함하므로 순수 터치 지연이 아닌 보수적인 관측값이다.
- 영상은 가변 FPS 원본 순서를 유지하여 분석했다. 962프레임 중 961개의 화면 코드를 Host draw 로그와 일치시켰다. 서로 떨어진 5개 시간 오버레이와 MP4 PTS의 기준 차이는 0.766ms 이내였다.
- Mac과 태블릿 시계 차이는 약 0.67초였다. 입력→녹화 반응 계산에는 같은 Android 시계를 사용하여 이 차이를 피했다.

## 입력 검증 결과

| 동작 | 관측 |
| --- | --- |
| 터치 | 활성화 이후 두 번의 down/up가 Host에 도착하고 태블릿 화면 상태 변화 확인. 일반 구간 약 131ms, 146ms |
| 터치 드래그 | 세 번의 down/move/up 전달 확인. 일반 구간 첫 반응 약 142ms, 160ms. 마지막 시도는 복구 정지와 겹쳐 약 1,145ms |
| 휠 이벤트 | 세 번의 Host scroll 수신 및 콘텐츠 위치/상태 변화 확인. 일반 구간 약 126ms, 140ms. 마지막 시도는 약 2,850ms |
| 물리 마우스 이동·버튼 | 사용자가 연결된 마우스가 없다고 확인. 미검증 |

첫 터치 시도는 Host down/up 기록이 없어 성공으로 세지 않았다. 창 활성화 클릭 가능성이 있으나 확정하지 않았다.
기본 ADB mouse MOVE 명령도 Host move 기록을 얻지 못했으므로 물리 마우스 동작의 대체 증거로 사용하지 않았다.
소표본이므로 위 값을 안정적인 p95나 모든 상황의 성능으로 일반화하지 않는다.

## 재현된 긴 정지

11:46:48.632 Android 로그에서 오른쪽 영상 gap과 paired IDR 요청이 발생했다.
Host 테스트 화면은 계속 갱신했지만 태블릿의 해당 화면 코드는 약 2.9초 동안 고정됐다.
11:46:50, 11:46:51 로그에 오른쪽 renderedFps=0이 기록됐다.

- 750ms 간격의 paired recovery IDR 재요청이 있었다.
- 왼쪽은 먼저 IDR을 받았지만 오른쪽 IDR이 늦어 좌우 복구가 완료되지 않았다.
- 오른쪽 gap→IDR 입력: 2,885.762ms, IDR 입력→출력: 9.063ms.
- 오른쪽 gap→복구 출력: **2,894.826ms**.

따라서 이 표본의 긴 정지는 디코더에 IDR이 들어온 뒤의 처리보다는 IDR을 확보하고 좌우 화면을
복구하는 대기에 집중되어 있다. 패킷 손실의 원인, Host IDR 생성·전송 지연의 비중, 녹화 부하의
영향은 아직 분리하지 못했다. 네트워크만의 문제 또는 Host만의 문제로 단정하지 않는다.

## 코드 검토와 자동 검사

입력 경로: `StreamActivity.forwardPointer` → JNI `session_io` → `InputScheduler` →
Host `CaptureSession+Input.validateAndInjectReliableInput` → `CGEvent.post` → ACK.

- 이동은 2×FPS 주기로 최신 상태를 합친다. 신뢰성 입력은 ACK를 기다리며 20ms 단위로 최대 12회 재시도한다.
- ACK 또는 입력 허용 표시는 Host 앱의 실제 처리·화면 반응을 증명하지 않는다.
- HUD LOSS/inputDrops는 영상 경로 지표이며 입력 scheduler drop과 다르다.
- `cargo test -p android-viewer input_protocol`: **11 passed**. 실제 입력 전달 증거는 위 실기 기록과 구분한다.
