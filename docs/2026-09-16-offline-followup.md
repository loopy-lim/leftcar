## 4K 화면 복귀

두 Surface 중 하나가 사라지면 기존 분할 렌더러가 멈추며 준비된 수신기와 미디어 키도 이미 소비된 상태가 된다. 이전 코드는 Surface가 돌아오면 같은 정보를 다시 붙이려 했고, 붙이기 실패 후에도 새 연결 준비를 요청하지 않아 검은 창으로 남을 수 있었다.

수정 경로:

1. 일시적인 분할 Surface 해제 또는 붙이기 실패를 기록한다.
2. 양쪽 Surface가 준비되면 기존 React/Host 복구 경로에 새 연결 준비를 한 번 요청한다. 이 상태에서 JNI 붙이기를 반복하지 않는다.
3. Host가 준비를 마친 새 연결 요청이 도착하면 복구 상태를 초기화하고 같은 Activity 창에 붙인다.
4. 교체된 예전 Surface의 늦은 종료 알림은 새 화면에 영향을 주지 않는다.

회귀 테스트는 실제 Activity 콜백을 실행하며 JNI와 React 이벤트 전달 경계만 대체했다. 수정 전에는 소비한 수신기에 반복 붙이기를 시도해 실패했고, 수정 후에는 한 번의 연결 준비 요청·같은 창 유지·새 요청 후 정상 붙이기를 확인했다. 실패한 새 연결에는 다음 복구 요청을 허용한다. 기존 화면 시계 테스트도 실패 후 새로운 Host 준비를 거치는 실제 흐름으로 갱신했다.

1440p는 소켓·암호 상태를 유지하고 Surface만 교체한다. 4K는 두 수신기를 함께 다시 준비하는 기존 복구 경로를 사용한다. 후자는 키·수신기 불일치 위험을 줄이지만 연결을 다시 준비할 시간이 필요하다. **4K 실제 영상 복귀, 복귀 시간, 물리 입력은 아직 검증하지 않았다.**

## 호스트 전송 대기 비교

기존 1440p 고변화 영상 로그의 AU 크기 181개를 사용했다. 이는 1초 간격 크기 샘플이며 전체 프레임 기록이 아니다. 키프레임 여부가 없으므로 델타 프레임으로 독립 재생했다. 각 샘플의 비트레이트와 FEC 수는 동일하게 유지했고 실제 `prepareUdpAccessUnit`·`paceUdpDatagram`을 실행했다.

실제 `networkQueue`의 userInteractive 우선순위(QoS 33)를 확인했다. 빌드 종료 후 수행했으며 활성 호스트 영상이 생기면 중단하도록 감시했다. 처리 순서를 바꿔 세 번 반복했다. 수치는 **각 회차 p95의 중앙값**이며, 합친 543개 샘플의 p95가 아니다.

| 조건 | 전송 대기 p95 | 다음 프레임에 이월되는 대기 포함 p95 | 전송 대기 16.67ms 초과 |
| --- | ---: | ---: | ---: |
| 기존 기록의 4/8개 묶음·기존 속도 | 20.99ms | 22.69ms | 148/543 |
| 16개 묶음·기존 속도 (원인 분리용) | 12.42ms | 15.83ms | 1/543 |
| 기존 custom16·2배 전송 속도 옵션 | 9.35ms | 11.40ms | 0/543 |

다음 프레임에 이월되는 대기까지 포함하면 custom16도 543회 중 3회 예산을 넘었다. 이 실험을 전체 성능 합격으로 해석하지 않는다.

16개 묶음은 운영체제의 대기·깨우기 횟수를 줄였다. custom16은 델타 영상의 대기를 추가로 줄였으며, 기존 정책상 복구 키프레임의 속도 제한은 유지한다. 전송량 자체를 줄인 실험은 아니며 모든 조건의 준비 패킷 수와 바이트 수가 같았다.

**확인한 것:** 호스트의 기존 전송 대기만으로도 60fps 시간 예산을 넘을 수 있고, 기존 custom16 옵션이 이 지연을 줄이는 유력 후보라는 점이다.

**확인하지 않은 것:** 암호화·실제 송신·Wi-Fi/Tailscale 손실·캡처·인코더·Android 디코더·물리 화면을 포함한 성능이다. 더 짧은 시간에 패킷을 보내는 선택이므로 수신 측 밀림과 손실을 실기로 비교해야 한다. 기본 설정을 바로 바꾸지 않았고, Parsec 수준 합격으로 취급하지 않는다. 초기 기본 스레드 실험(v1)은 실제 전송 큐 조건이 달라 결론 표에서 제외했다.
