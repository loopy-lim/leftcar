# Lenovo 입력·영상 성능 검증 — 2026-09-16

## 현재 판정

후속: 두 손가락 스크롤은 사용자가 동작을 확인했다. Lenovo 실기는 사용자의 외부 일정으로 보류 중이다. 이후의 4K 복귀 수정 및 호스트 pacing 비교는 [실기 보류 중 작업 기록](2026-09-16-offline-followup.md)에 기록했다. 아래 실기 성능 표는 당시 후보의 결과로 유지한다.

**성능 합격 전이다.** Lenovo TB710FU의 1440p가 가장 낮은 지연을 보였지만, 3분 고변화 영상 시험에서 지연과 복구 횟수 기준을 넘었다. 4K는 처리량이 60fps에 가까워도 지연이 컸다. Parsec과 같은 조건의 비교나 광학 지연 시험은 수행하지 않았다.

## 고정한 기준과 측정 범위

- 최소 1440p, 목표 60fps. 유효 샘플의 90% 이상에서 57fps 이상.
- 비교당 180초 이상, 전체 화면이 계속 변하는 동일 WebGL 장면.
- 캡처부터 Android Surface 전달까지 주기적으로 기록한 지연의 p95 ≤ 50ms.
- 네트워크 왕복 지연 p95 ≤ 20ms.
- 새 프레임 누락, 복구, 송신 실패, 비트레이트 하한 압박 모두 0.
- 물리 키보드·마우스 검증은 별도이며 합성 이벤트나 단위 테스트로 대신하지 않는다.
- Surface 전달은 소프트웨어 단계다. 패널에 실제 빛이 표시되는 시점, 물리 입력부터 표시까지의 지연은 포함하지 않는다. Split은 두 타일의 예정 Surface 전달 시각이다.

1440p의 두 복구 직전 수신 지연이 127ms와 129ms까지 증가했다. 이후 각 9개 AU를 건너뛴 `recoverySkip` 로그와 35ms 수준으로 돌아온 지연이 관찰됐다. 이는 유실 카운터 증가 없이도 밀린 영상을 따라잡는 복구가 발생했음을 뜻한다. 송신 pacing p95 스냅샷의 중앙값은 19.36ms, p95는 20.53ms였다. 다음 비교 대상은 기존의 16-datagram custom pacing 설정이며, 이것이 원인인지 아직 실기로 증명하지 않았다.

4K에서 송신 부하 판단을 단일 패킷의 최악 송신 시간으로 맞춘 S1 수정은 구현의 불일치를 해소했지만 합격으로 이어지지 않았다. 낮은 RTT와 송신 실패 0만으로 전체 전송 경로가 원인에서 제외되는 것은 아니다.

## 인코더만 분리한 비교

V3 도구는 실제 인코딩에 성공한 프레임의 지연과 버린 프레임의 콜백을 구분한다. 900개 합성 NV12 프레임, 목표 60fps, 타일당 30Mbps, 최대 동시 입력 5개 조건이다. 캡처·네트워크·Android·화면 표시는 포함하지 않는다.

| 방식 | 성공 출력 속도 | 성공 프레임 콜백 p95 | 인코더가 버린 프레임 | 판단 |
| --- | ---: | ---: | ---: | --- |
| 1440p RTVC | 59.49fps | 11.61ms | 8/900 | 짧은 처리 지연, 순간 누락 있음 |
| 1440p AVE | 59.90fps | 38.49ms | 0/900 | 처리량 유지, 지연 증가 |
| 4K 양쪽 AVE | 각 59.89fps | 40.24 / 39.67ms | 각 0/900 | 4K 처리량 확보에 유리 |
| 4K 양쪽 RTVC | 각 44.96fps | 12.99 / 12.86ms | 각 107/900 | 성공 프레임은 빠르지만 60fps 미달 |

앞선 V1 시험에서 AVE 동시 입력 한도를 2개로 낮추면 약 54.72fps로 떨어졌다. 3개는 약 59.72fps, 5개는 약 59.85fps였다. 무조건 큐를 줄이면 지연 문제 대신 처리량 문제가 생길 수 있다. V1의 콜백 지연은 버린 프레임을 포함하므로 성공 프레임 지연 비교에는 V3만 사용한다.

V3 실행 중 태블릿 스트림이 시작되면 중단하도록 감시했다. 네 번 모두 독립 시험으로 완료됐다. 원본: `encoder-v3-*-receipt.json`, `encoder-v3-*.json`.

## Lenovo 두 손가락 스크롤

물리 조작 기록에서 Android `CLASSIFICATION_TWO_FINGER_SWIPE` MOVE가 앱까지 도착했다. 하지만 휠 축과 전용 스크롤 거리 축이 모두 0이었다. 기존 코드는 이 값을 읽어 스크롤 양이 없다고 판단했다.

수정은 이 분류가 붙은 제스처에서만 이전 위치와 현재 위치의 차이를 대체값으로 사용한다. 전용 거리 축이 있으면 그대로 사용하고, 제스처 종료·취소·일반 포인터 이동 시 기준 위치를 초기화한다. 일반 마우스 이동을 스크롤로 바꾸지 않는다.

[AOSP GestureConverter](https://android.googlesource.com/platform/frameworks/native/+/a5ea7c1785/services/inputflinger/reader/mapper/gestures/GestureConverter.cpp)의 가상 손가락 좌표와 스크롤 거리 방향을 참고했다. Lenovo에서 실제 위치 차이로 스크롤이 발생하는지 확인하는 단계는 남아 있다.
