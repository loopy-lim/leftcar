# Lenovo 입력·창 유지 및 성능 검증

2026-09-16 KST. TB710FU (`192.168.0.19:5555`), 일반 앱 `leftcar.ll3.kr`.

> 이 문서는 창 유지 변경 직후의 1차 검증 기록이다. 이후 입력 엔진과 Host를 갱신한 현재 결과는 [입력·성능 후속 검증](2026-09-16-input-performance-validation.md)을 따른다. 아래의 설치물·정리 상태·성능 수치는 1차 시점의 기록이다.

## 결과

- 메인 창만 닫아도 이미 열린 영상 창과 스트림이 유지된다. 최종 APK에서 30.21초 / 31개 JSON 표본 모두 같은 세션이 실행 중이었고 프레임 수가 증가했다.
- 마우스 출처의 Android Back 입력은 소비한다. 일반 Back은 확인창을 열며, `계속 보기`는 유지하고 `화면 닫기`는 해당 영상 창만 종료한다.
- 메인 창을 다시 열어 제어 연결이 바뀌고, 영상이 가려져 Host의 약 6초 무응답 정리가 발생한 경우에도 같은 영상 창에서 새 세션으로 복구했다.
- 메인 창이 없는 상태에서 영상 창을 명시적으로 닫은 뒤 메인 창을 다시 열어도 영상이 저절로 재생성되지 않았다.
- 성능 비교용 Android 패키지 `leftcar.ll3.kr.benchmark.audit_candidate`, `leftcar.ll3.kr.benchmark.audit_baseline`을 제거했다. 최종 기기 패키지 목록에는 일반 Leftcar 하나만 남았다.
- **60FPS 성능 기준은 미통과다. Parsec 수준 또는 입력 지연 개선을 입증한 결과가 아니다.**

이 창 유지 동작은 앱의 메인 Activity 종료에 대한 것이다. 앱 강제 종료, 프로세스 사망, 기기 재부팅까지 영상 창을 보존하는 기능은 아니다.

## 변경 이유와 동작

기존 카탈로그 화면의 정리 함수는 소유한 모든 스트림 예약을 해제했다. Android 영상 창은 별도 Task로 열려도 메인 화면을 닫으면 이 정리 함수가 실행되어 영상까지 닫혔다. 실행 중인 스트림과 예약을 Host별 앱 메모리 저장소로 옮겼다. 화면을 아직 열지 못한 대기 작업만 카탈로그 종료 시 취소한다.

수신 피드백 타임아웃은 기존 창을 유지하는 복구 경로로 보낸다. 메인 화면 재진입 시에는 새 Host 상태 조회가 성공한 뒤 상태를 판단하고, 각 복구 작업은 현재 연결을 새로 고정한다. 이미 진행 중인 작업에서 컴퓨터 선택이 바뀌면 계속 취소되므로 다른 컴퓨터로 작업이 넘어가지 않는다.

실기 재진입 시험에서 두 문제를 추가로 수정했다.

1. 네이티브 모듈을 객체 펼치기로 복사하면 열거되지 않는 메서드가 누락됐다. 준비 실패 정리 중 `cancelPreparedStream`을 찾지 못해 원래 오류까지 가려졌다. 메서드를 원래 모듈에 전달하면서 예약 보호가 필요한 호출만 감싼다.
2. 유지된 영상 창이 최초 연결의 선택 세대를 계속 참조했다. 메인 창이 같은 컴퓨터에 새로 연결한 뒤 복구하면 `Host selection changed`가 발생했다. 영상 창이 속한 컴퓨터와 현재 컴퓨터를 확인하고 작업 시작 시점의 연결을 사용한다.

작업 시작 전부터 진행 중이던 HUD 칩 제거는 보존했다. 제거된 API를 참조하던 기존 테스트를 정리했고, Rust·Host·Swift의 기존 변경은 수정하거나 설치하지 않았다.

## 성능 표본

녹화·스크린샷 없이 Host 상태를 약 1초마다 JSONL로 수집했다. XR 스트림도 계속 실행 중이었다. 프로필별 실제 해상도와 인코더 모드를 확인했다.

| 표본 | 해상도 / 목표 | 기간 / 표본 수 | 수신 FPS p50 / p95 | 추가 gap / 복구 | 판정 |
| --- | --- | --- | --- | --- | --- |
| 균형 | 2560×1440 / 60 | 61.47초 / 62 | 43 / 49 | 1 / 1 | FAIL |
| 빠른 반응 | 1920×1080 / 60 | 61.60초 / 62 | 55 / 57 | 2 / 2 | FAIL |

빠른 반응 표본은 수신 FPS 한 값이 누락됐다. 분위수에는 유효한 61개만 사용하되, 합격 판단에서 누락을 제거하지 않아 telemetry 기준도 실패한다. 두 표본 모두 송신 오류와 비트레이트 최저값 붕괴의 추가 횟수는 0이었다.

두 구간의 데스크톱 내용과 브라우저 상태가 같지 않아 통제된 A/B 비교가 아니다. 1080p에서 더 높은 수치를 관측했지만 해상도만의 개선 효과로 단정하지 않는다. 이전 APK의 짧은 시작 구간도 동등한 비교 기준으로 사용하지 않는다.

입력 RTT, split wire/capture age는 두 표본 모두 유효 값이 없어 `null`로 남겼다. 별도의 로컬 입력 페이지 시험도 키보드 문자·포인터 전체 동작과 지연을 검증할 만큼 일관된 도착 기록을 얻지 못했다. 임시 HTTP 수집기의 직렬 처리로 인한 기록 지연 가능성도 있어 그 시각을 입력 지연으로 계산하지 않았다. **실제 키보드·마우스 및 입력→화면 광자 지연은 미검증이다.**

## 다시 측정하는 방법

추가 Android 앱을 설치하지 않고 일반 앱에서 스트림을 연다. 처음 시작한 구간은 분리하고, 동일한 움직임·해상도·인코더·네트워크·동시 스트림 조건을 유지한다.

```sh
python3 tools/stream-stats.py --device TB710FU --duration 62 --log /tmp/leftcar-run.jsonl
python3 tools/stream-gate.py --log /tmp/leftcar-run.jsonl --min-duration 60 --report /tmp/leftcar-run-summary.json
```

현재 기본 합격 기준은 움직임 표본의 90% 이상에서 목표 FPS의 95% 이상이다. 최소 10개 움직임 표본, 기본 최소 10초와 최대 2.5초 수집 간격을 검사한다. 위 명령은 최소 기간을 60초로 늘린다.

- 모든 표본에서 선택 세션이 존재하고 `running`이어야 한다. 여러 세션이 섞이면 `--session`으로 선택한다.
- 수집 실패, 수신 FPS 누락, 불완전하거나 바뀐 해상도·목표 FPS·인코더 모드, 카운터 초기화를 합격에서 제외한다.
- gap·복구·송신 오류·비트레이트 붕괴의 추가 발생을 검사한다.
- 움직임 표본이 부족하면 `UNKNOWN`이다. 종료 코드는 PASS=0, FAIL=1, UNKNOWN=2다.
- p50/p95는 **상태 스냅샷 값들의 분위수**다. 프레임별 또는 입력 이벤트별 p95가 아니다. RTT 자체가 평활된 값일 수도 있다.

다음 성능 작업은 같은 동작을 재생하는 통제된 표본에서 캡처·인코더의 공급 FPS와 수신 측 손실·복구 시간을 먼저 분리해야 한다. 입력 ACK 통계가 실제로 보고되는지도 별도로 확인해야 Parsec와 지연을 비교할 수 있다.
