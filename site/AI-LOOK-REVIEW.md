## 2. 디자인 축 상세

### A1. 히어로가 "SaaS 랜딩 템플릿의 첫 화면" 공식을 그대로 따른다 — P1
- **근거**: `src/components/Hero.tsx:9-19` — 배지 pill → 중앙정렬 헤드라인 → 중앙정렬 subcopy → CTA 2개(주 accent + 보더 보조) → 아래 다이어그램. `src/components/Hero.css:37-75`의 `.hero-ctas`(중앙 flex) + `.primary-cta`(accent 배경)/`.secondary-cta`(투명+보더) 조합. 이 순서·조합은 AI 생성 랜딩에서 가장 빈출한 골격이며, DESIGN-AUDIT C4가 "과적"만 다뤘을 뿐 **골격 자체는 그대로**다.
- **왜 AI 티인가**: 배지→헤드라인→2 CTA는 수천 개의 생성 페이지가 공유하는 배열이다. 특히 pill 배지가 "MIT 라이선스 · 오픈 소스 · v0.1.4"라는 **사실 전달용 텍스트**를 담고 있는데, 이 정보는 pill이 아니라 그냥 텍스트 한 줄이면 된다. 장식이 정보보다 앞선다.
- **대안** (난이도 중 · 임팩트 상):
  1. 배지 제거 → 헤드라인 위 짧은 도입 텍스트 한 줄로 강등: "PC 화면을 폰으로 보는 작은 도구입니다. v0.1.4, MIT." — pill 크롬 없이 `--text-sm` `--text-dim`으로.
  2. 헤드라인+subcopy는 중앙정렬 유지하되 CTA 행을 좌측 정렬로 꺾어 완전 대칭을 깬다(또는 반대). 한 요소만 비대칭이어도 "템플릿 냄새"가 크게 줄다.
  3. CTA 라벨에서 버전 제거: "v0.1.4 Viewer APK 받기" → **"APK 받기"**. 버전은 배지/Status에 이미 있고, 라벨에 버전을 박는 것은 릴리스마다 코드 수정을 강요하는 마케팅 문구 리듬이다.

### A2. 폰트 스택이 시스템 UI 기본값 — 아이덴티티의 부재 — P1
- **근거**: `src/index.css:32` — `font-family: -apple-system, BlinkMacSystemFont, "Segoe UI", Roboto, "Apple SD Gothic Neo", "Malgun Gothic", "Noto Sans KR", sans-serif`. DESIGN-AUDIT §2.1이 **크기** 스케일은 토큰화했지만 **글꼴 자체**는 untouched. 결과: 기기 기본 산세리프 = 수많은 생성 페이지와 동일한 외형.
- **왜 AI 티인가**: 폰트 선택은 인간 디자이너가 남기는 가장 뚜렷한 취향의 흔적인데, 이 페이지에는 그 흔적이 없다. 토큰·간격이 아무리 정돈돼도 "시작하자마자 붙인 기본 스택"은 바로 드러난다.
- **대안** (난이도 중 · 임팩트 상):
  1. **헤드라인 전용 디스플레이 서체 1개**만 추가(본문은 시스템 유지 — 비용 최소, 대비 최대). 한국어 기준 예: 헤드라인에 고스트럭 계열(예: "Pretendard"가 아니라 **개성 있는 후보 2개 이상 비교 후 확정** — 모든 사이트가 Pretendard를 쓰는 지금은 Pretendard조차 새로운 기본값이 됐다). 후보 방향: (a) 약간 무게 있는 제조/툴 느낌의 산세리프, (b) 헤드라인만 영문+숫자에 모노스페이스 계열을 섞어 "로컬 툴" 기계적 성격 표현.
  2. 라이트(종이) 배경으로의 전환은 A5와 묶어 판단.

### A3. 다이어그램이 "AI가 그리는 추상 모식도"의 정석 — P1
- **근거**: `src/components/Diagram.tsx:5-29` — 빈 `<div>` 직사각형들(PC 화면 2개, 안드로이드 창 3개) + 점선(`.network-line`, `Diagram.css:50-63`) + **텍스트 화살표 `"→"`**(`Diagram.tsx:13`) + 라벨 "로컬 네트워크 · 암호화". 내용이 없는 테두리 상자를 점선으로 잇는 구도는 AI 생성 랜딩의 상징적 패턴이다. 히어로 헤드라인 바로 아래 페이지에서 가장 큰 시각 요소가 이 "빈 상자 그림"이라는 점이 문제.
- **왜 AI 티인가**: 사람이 만든 툴 페이지는 이 자리에 **실물 증거**(스크린샷, 실제 앱 화면)를 놓는다. 증거 없는 모식도는 "보여 줄 게 없다"는 인상을 준다.
- **대안** (난이도 중~대 · 임팩트 상):
  1. 최선: 실제 앱 스크린샷(PC 캡처 + Android 폰 프레임 1장)으로 교체. 존재하지 않으면 ↓.
  2. 차선: 다이어그램 **삭제**. 히어로는 헤드라인+subcopy+CTA로 끝내고, Features 첫 카드("여러 화면, 여러 창")가 시각화 역할을 대신한다. "없음"이 유일하게 AI 티가 안 나는 선택지다.
  3. 유지한다면 최소한 내부에 실제 어휘 넣기: 빈 `.window-body` 대신 창 제목 텍스트("디스플레이 1", "디스플레이 2")와 실제 전송 항목 라벨("화면", "입력") — 빈 상자가 아니라 문서 다이어그램처럼.

### A5. 다크 네이비 + 청록(teal) accent — 생성 페이지 기본 팔레트 — P3
- **근거**: `src/index.css:2-8` — `--bg: #0b0e14` / `--surface: #11151f` / `--accent: #4cc2a8`. 어두운 남색 배경 + 민트/청록 포인트는 AI 생성 다크 랜딩의 가장 흔한 조합.
- **왜 AI 티인가**: DESIGN-AUDIT §2.3이 accent **사용처**는 3종으로 제한했지만 색 자체의 선택 근거는 없다. 이 팔레트는 "개발자 툴이면 일단 다크+청록"이라는 무비판 관습의 산물.
- **대안** (난이도 대 · 임팩트 중): (a) 라이트 종이 톤 배경 + 잉크 계열 텍스트 + accent 1색 — 로컬 유틸리티의 담백한 문서 느낌. (b) 다크 유지 시 accent를 teal이 아닌 브랜드 고유색(프로젝트명 "Leftcar"의 방향성, 예: 주황/노랑 계열의 신호색)으로 교체. 다만 전면 색상 교체는 정보 위계 재검증이 필요해 후순위. **결정 기록 필요** — "왜 다크인가/왜 이 색인가"에 답이 없으면 그 자체가 AI 티의 근거다.

### B1. 독자를 안 맞춰 입은 사양 나열형 문장 — P1
- **근거**: `src/content/site.ts:79` — "QR로 핀된 호스트 Ed25519 키 핸드셰이크 뒤 ChaCha20-Poly1305 AEAD로 봉인합니다." 그 외 `:37` "JavaScript를 거치지 않는 별도 네이티브 데이터 경로", `:44` "포인터 전송률은 영상 FPS의 2배로 제한됩니다".

- **대안** (난이도 소 · 임팩트 상) — 독자 언어로 번역하되 사실은 유지:

- **"Rustra는"의 원 의도 단어 미확정** — 이 문서에서도 확정하지 않음. 구현 전 사용자 확인 필수(DESIGN-AUDIT §3-11과 동일).

- A2 폰트 도입은 라이선스(웹폰트 self-host 조건)와 성능(budget) 확인 필요.
